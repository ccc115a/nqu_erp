## 2　為什麼「只是把 api 多開幾台」不是答案

### 2.1　三層各自的擴展性

| 層 | 是否無狀態 | 能不能水平複製 | 瓶頸 |
|----|-----------|---------------|------|
| web(nginx 靜態) | ✅ 完全無狀態 | ✅ 可無限複製 | 幾乎不會是問題(CDN 級) |
| api(Rust binary + DB 連線池) | ✅ 無狀態(session 在 JWT) | ✅ 可複製 | **複製再多,全打同一顆 DB** |
| db(Postgres 單一) | ❌ **有狀態** | ⚠️ 讀可複製、寫不可 | **真正的瓶頸、唯一狀態來源** |

### 2.2　直接結論

```
全校同時選課 5k–2 萬:
  api 開 3 個 replica  →  3×456 個連線全打到同一顆 Postgres
                        →  唯一瓶頸 = DB
                        →  水平擴 api 只是把壓力集中到同一顆 DB
```

### 2.3　DB 才是真瓶頸的三條證據

1. **所有「戰鬥路徑」都繞 DB**:加選 = INSERT enrollments + 扣 capacity + 查衝堂,同一筆交易。
2. **寫路徑不能複製**:只能有一顆主庫接受寫。讀可開 replica,寫不可。
3. **選課高峰是「寫」高峰**(人人搶課=人人寫),不是讀高峰——**read replica 救不了選課,只救得了查課表**。

> 這正是書 06.md **6.6「何時才該考慮 k8s」判準**的實證:瓶頸在 DB,api replica 再多都是把壓力集中到同一顆 DB 上。

## 3　怎麼做:擴展階梯(按成本與收益排序)

### L1　先限流,別先擴容(最便宜、最貼合選課)

選課高峰的本質是「瞬間碰撞」,不是「穩定高流量」。**用「擋」比用「擴」誠實**:

- api 對 `/enrollments` 加 **rate limit**:每 token 每分鐘 N 次,超 429 + `Retry-After`(書 6.4 L2 已設計)。
- **排隊替代擴容**:高峰改「送出即排隊 → 輪到才處理」,而不是「硬扛到 timeout」。把溢流擋在入口,而不是讓它打到 DB 內爆。

> 這正是 6.4「AI 自癒」L2 保護性行為(429)的落地版。

### L2　api 水平複製(映像已備好,只差 compose 開 replica)

CD(GHCR)已把 api 映像推到 `ghcr.io/ccc115a/nqu_erp-api:main`(書 6.2 / v0.5)——複製 api **不必重編譯**,只要:

```bash
# 同一映像、開第二支 api(對齊書 6.5 的 docker_run.sh WEB_PORT 哲學)
docker run -d --name nqu-api-2 \
  --network nqu_erp -e DATABASE_URL=... \
  -p 8081:8080 ghcr.io/ccc115a/nqu_erp-api:main
```

但**複製 api 的前提**是「瓶頸已移出 DB」(書 6.6 判準)——若壓測發現「api 單 replica 就扛得住、DB 才是 90% 時間線」,那這步可以跳過。

### L3　DB 讀寫分離(真正的瓶頸層)

選課高峰能砍的是「讀」流量(查課表/查已選/查名次),這些**可以打到 replica**:

```yaml
db-replica:
  image: postgres:16-alpine
  environment: { ... 同主庫 ... }
  depends_on: [db]
```

api 連線時依「讀寫分流」:寫(加選/退選)走主庫,讀(查課表/成績)走 replica——但**這需要 api 改 code**(連線池拆兩顆)。**成本在 api,不是 infra。**

> 務實順序:官方文件一再強調「**先用好單機 Postgres,再談 replica**」。NQU-ERP 現在連 `docker_run.sh` 的 `max_connections`/`shared_buffers` 都還沒調(預設值)。**先把書上「單機調教」做完,再看 replica。**

### L4　(真正的)單一 DB 瓶頸:預算好高峰,而不是硬扛

如果真做到 5k 同時、每秒幾千寫,單一 Postgres 寫再多調教都到頂——那時的選項:

| 方案 | 成本 | 適用 |
|------|------|------|
| 寫入批次 / 延遲扣容量 | api 改 code | 每個 enroll 不必「即時扣 capacity」→ 高峰先記、離峰批次扣 |
| 分庫(shard by course) | 爆炸貴 | 只有「真的萬級同時寫」才談 |
| 換 managed DB(RDS) | 貴但省維運 | 有預算、學校願意把 DB 交給雲 |

> 到這一步才需要認真談 k8s的替代——不是「別人都上了」,而是「DB 真的需要跨機」。書 6.6 判準第 4 條(跨機 HA=要 Stateful)才第一次轉真。
