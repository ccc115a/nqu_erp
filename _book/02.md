# 第二章　需求工程

> 「做一個選課系統」是一句話，「選課系統必須做到 O 與 X，且不允許 Y」才是需求。本章從模糊意圖走到可執行的規格，全程以 NQU-ERP 的 `_doc/plan.md` 與 `src/handlers/enrollment.rs` 為例。

---

## 2.1　需求的本質：從模糊意圖到精確規格

需求工程的第一課：**使用者交付的是「意圖」，不是「規格」**。意圖是模糊的、隱含假設的；規格是精確的、可測試的、無歧義的。金字塔：

```
        意圖（Intention）
     「要做一個校務系統」
          │  需求分析（問問題、驗證假設）
          ▼
        功能需求（Functionality）
     「學生能選課、看重成績」
          │  需求規格化（寫成可測試的句子）
          ▼
        規格（Specification）
     「POST /enrollments 對已選過(ENROLLED)的課回 success=false」
```

「精確」的判準是：**兩個不同的人讀同一份規格，對同一個輸入會得到同一個預期的行為**。若做不到，就是還不夠精確。

### 本專案例子：一句話 → 一張規格表

`_doc/plan.md` 開頭就是校務系統 MVP 的意圖，但整份文件迅速把它升級成可驗證的規格：

- 系統概述：服務「學生、教師與教務處」三類使用者（→ 後續變成 RBAC 三角色）
- 功能表：學生加退選（即時名額、3 步驟內完成）、教師成績登錄鎖定、管理員開課與帳號管理
- **成為規格的關鍵**：每一項都有「可被測試的行為描述」，例如：

| plan.md 的寫法 | 變成規格的依據 |
|----------------|----------------|
| 「衝堂檢查」 | 定義了精確條件：`(DayA == DayB) AND (StartA <= EndB) AND (StartB <= EndA)` |
| 「原子化名額扣減」 | 定義了 SQL：`UPDATE courses SET enrolled_count = enrolled_count + 1 WHERE … AND enrolled_count < capacity` |
| 「退選」 | 定義了副作用：`status='DROPPED'`、名額減一、刪除成績紀錄 |
| 「成績鎖定」 | 定義了狀態機：`is_submitted=false（可改）→ true（不可改）` |

把「意圖」寫成這種「條件 + 動作 + 副作用」的句子，就是**把需求變成規格**的過程。這些句子後來大多變成 `test.sh` 裡的一條 `assert_*`（第五章會講）。

## 2.2　需求挖掘與訪談技巧

需求不會自己出現，需要被「挖」。常用的技術：

1. **利害關係人訪談（Stakeholder Interview）**：問正確的人正確的問題。
2. **觀察與沉浸（Observation）**：看使用者實際怎麼做事，往往和他們「說」的不一樣。
3. **原型（Prototyping）**：做一個可以點的假介面，讓使用者看到才算得準。
4. **優先權排序（Prioritization）**：MoSCoW（Must / Should / Could / Won't）區分必要與不必要。

訪談的金科玉律：**不要問「你想要什麼功能」，要問「你現在怎麼做事、哪裡最痛」**。功能是解法，痛點才是需求。

### 本專案例子：三位使用者的需求訪談

假設我們訪問教務處承辦人，談「選課」：

| 訪問者問 | 典型回答 | 挖出的需求 |
|----------|----------|------------|
| 現在開學加退選是怎麼做的？ | 「用 Excel 收表，人工核對有沒有衝堂，很怕超收」 | 自動衝堂檢查、名額上限、防超收 |
| 學生退選後想再選同一門課呢？ | 「不行，退了就退，不然紀錄會亂」 | **退選後不可重選**（程式裡的第一個 edge case） |
| 教務處最怕什麼事？ | 「教師改成績不通知，成績送出去後還有人偷改」 | 「送交鎖定」：`is_submitted` 狀態機 |
| 如果課程改時間，選課資料會亂嗎？ | 「會啊，我們現在要手動一筆一筆改」 | 課程刪除要 Transaction 清理關聯資料（`admin.rs`） |

這些答案沒有「高中生面試式的功能清單」，而是**業務痛點**。NQU-ERP 的 `v0.3.1` 就反映了一次典型的訪談迭代：管理員回饋「只能新增帳號/課程，改錯或建錯不能刪，很痛苦」→ 下一版就是「修改/刪除帳號與課程」。**需求挖掘是持續過程，不是一次性活動。**

## 2.3　用例建模與使用者故事

### Use Case

Use Case 描述「**某個角色在某種情境下，想達成某個目標**」，格式：

```
用例名稱：學生加選課程
主要參與者：學生
前置條件：已登入、課程存在
主流程（Happy Path）：
 1. 學生送出加選請求
 2. 系統檢查：是學生身分
 3. 系統檢查：未選過此課
 4. 系統檢查：無衝堂
 5. 系統檢查：名額未滿
 6. 系統回傳「加選成功！」
替代流程：
 A1. 衝堂 → 「課程時間衝突！…」
 A2. 名額滿 → 「課程名額已滿」
 A3. 重複加選 → 「您已選修過此課程」
例外流程：
 E1. 不是學生 → 403
```

把 `src/handlers/enrollment.rs` 的主流程對照上面，會發現程式碼的結構幾乎就是用例的鏡像——**好的用例可以直接對映到程式碼的分支**。

### User Story

User Story 是敏捷常用的精簡形式：**「作為〈角色〉，我希望〈功能〉，以便〈效益〉」**。

- 「作為學生，我希望一進網站就能看到這學期的課程清單，以便快速比較要選哪幾門。」→ v0.2 課程瀏覽頁（`CourseList.tsx`）
- 「作為教師，我希望成績送出後就鎖住，以免學生質疑公平性。」→ `grade.rs` 的 `is_submitted` 鎖定
- 「作為管理員，我希望能刪除建錯的課程，以便維持資料正確。」→ v0.3.1 `delete_course`

### 角色模型與 RBAC

NQU-ERP 把「角色」直接做成系統的第一公民：

```rust
impl AuthUser {
    pub fn is_student(&self) -> bool { self.role == "STUDENT" }
    pub fn is_teacher(&self) -> bool { self.role == "TEACHER" }
    pub fn is_admin(&self) -> bool  { self.role == "ADMIN" }
}
```

每個 handler 的第一行幾乎都是角色檢查。這顯示：**需求階段的「誰可以用什麼」直接落成實作階段的 RBAC（Role-Based Access Control）**。前端也同步：`roles.ts` 定義每種角色的首頁，`PrivateRoute.tsx` 在角色不符時重導向。三角色的權限表（來自 `_doc/plan.md`）：

| 功能 | STUDENT | TEACHER | ADMIN |
|------|---------|---------|-------|
| 課程查詢 | ✅ | ✅ | ✅ |
| 加退選 | ✅ | ❌ 403 | ❌ 403 |
| 成績登錄/送交 | ❌ | ✅ | ❌ |
| 帳號/課程管理 | ❌ | ❌ | ✅ |

## 2.4　邊界條件與 Edge Cases

需求工程最常被忽略、卻在正式系統上線時造成最多災難的部分就是 **Edge Cases**。Happy Path 寫得再好，只要一個邊界沒處理，真實世界就會教訓我們。

常見的邊界來源：

1. **資料不存在**：要刪除的帳號不存在、要改成績的選課紀錄不存在。
2. **輸入不合法**：日期的年份帶了空白、成績超過 100。
3. **狀態不符**：成績已送交卻又想改、帳號已退選。
4. **權限邊界**：教師看別人的課程名冊、管理員刪除自己。
5. **資源極限**：名額為 0、容量剛好等於已選人數、同時最後一名加選。
6. **身分衝突**：admin 自己就是使用者，刪除自己會把系統鎖死在門外。

### 本專案例子：NQU-ERP 的 edge case「目錄」

把 `enum + messages` 一個一個撈出來，就是一份活的需求文件。這裡只列 `enrollment.rs` 與 `admin.rs` 的一部分：

| Edge Case | 判斷條件 | 回應 |
|-----------|----------|------|
| 非學生加選 | `!auth.is_student()` | 403「只有學生可以選課」 |
| 重複加選（狀態 ENROLLED） | 已存在 ENROLLED 紀錄 | `success:false`「您已選修過此課程」 |
| 退選後重選 | 已存在 DROPPED 紀錄 | `success:false`「已退選課程，請聯繫教務處重新選課」 |
| 衝堂 | 區域重疊 | `success:false`「課程時間衝突！…星期一 第6~8節」 |
| 名額滿 | `enrolled_count >= capacity` | `success:false`「課程名額已滿」 |
| 課程不存在 | DB 找不到 | 404「課程不存在」 |
| 退選不存在的選課紀錄 | 找不到 ENROLLED | 404「未找到選課紀錄」 |
| 管理員刪除自己 | `user_id == auth.user_id` | 400「不能刪除自己」 |
| 刪除有授課的教師 | 該教師仍有 courses | 400「該教師尚有授課課程，無法刪除」 |
| 刪除有選課的學生 | 該學生仍有 enrollments | 400「該學生尚有選課紀錄，無法刪除」 |
| 教師看非自己課程名冊 | `course.teacher_id != auth.user_id` | 403「非您授課的課程」 |
| 成績已送交再修改 | `g.is_submitted` | 403「此課程成績已送交，無法修改」 |

注意兩個特點：

1. **幾乎每一條都對應「一個 model 狀態 + 一個判斷」**，是可列舉、可測試的規格，不是主觀感受。
2. **錯誤訊息的品質本身就是需求**。衝堂不是回「參數錯誤」，而是回「與已選課程在星期 1 第 6~8 節重疊」——把**使用者能據此行動的資訊**放進訊息，這在第五章的 LLM-as-a-Judge 會再登場。

> **方法**：做 Edge Cases 時，對每個 actor 的每支 API，都問「如果輸入是空/不存在/重複/越界/狀態錯誤，結果是什麼？」，並把答案寫成清單。

## 2.5　AI 輔助需求分析：Red Teaming Prompting

### 原理

大型語言模型可以當一個「**紅隊（Red Team）**」：專門攻擊你規格的空洞。人類寫完需求初稿後，讓 AI 扮演「最難纏的使用者/最刁鑽的 QA」，用力找破口。這個技巧就叫 **Red Teaming Prompting**，它把需求審查從「等人類想到」變成「有系統地叫人（AI）想」。

基本流程：

1. 把「現有規格/短文」交給 AI，並聲明規則：**只能找問題，不修問題**。
2. 提供角色與約束：列舉可疑領域（權限、併發、資料一致性、錯誤回復）。
3. 要求輸出**可測試的邊界情境清單**，不要空泛意見。
4. 人一一評估 AI 的建議：哪些是假的、哪些是真破口，再決定要不要進規格。

### 本專案例子：對「加退選」做一次 Red Team

假設規格只有一句：「學生可以加選與退選課程。」對它做 Red Teaming，把結果分成「已經涵蓋」與「缺口」：

**AI 紅隊建議（節錄）→ 人的判讀：**

| AI 提出的問題 | 判讀 | NQU-ERP 實際定位 |
|---------------|------|------------------|
| 學生同一位老師的課衝堂也算嗎？ | 算，只要是同時段 | ✅ 已涵蓋（只看時段，不看老師） |
| 退選後再選同一門課？ | 教務處立場：不可 | ✅ 已涵蓋（DROPPED 即鎖） |
| 選課到一半課程被刪掉？ | 併發/一致性問題 | ⚠️ 部分涵蓋——課程刪除本身有 Transaction，但「選課當下課程消失」仍可能在邊界掉到 404 |
| 成績已送交的課，學生還能退選嗎？ | 真實哇！ | ❌ **規格缺口**：目前退選會直接刪掉成績紀錄，若成績已送交，退選等於抹掉已送交成績。教科書故意留一個缺口讓學生討論 |
| 名額最後一個，兩人同時按加選？ | 超賣風險 | ✅ 已涵蓋方向：名額扣減在 Transaction 內，但嚴格說仍是「先讀後寫」，需要條件式 UPDATE 才真正原子（見第三章） |

透過這個練習我們看到 Red Teaming 的價值：**AI 提是提得爛帳一堆，但其中常常有 1–2 條人類確實漏掉的真問題**。而「判斷哪條是真的」責任永遠在人。

**可用的紅隊 Prompt（以本專案為例）：**

```
你是一位刁鑽的需求審查員。以下是「選課系統」的規格：
<把你的規格貼進來>
請不要修改規格。只找出遺漏的邊界情境，聚焦在：權限、重複操作、
併發、資料一致性、錯誤回復。
每個情境請用「條件 → 系統該回應什麼」的格式輸出，並標註嚴重度（高/中/低）。
若某情境你判斷規格已涵蓋，不要列出來。
```

> 反模式：直接把 AI 的輸出全部照單全收進 JIRA。紅隊的輸出一律視為「候選」，人必須逐一驗證。

## 2.6　Spec-Driven Development：可執行的規格

傳統規格（Word 文件）有個致命缺點：**文件說「應該」，程式碼說「現在」**，兩者必然隨時間分道揚鑣。Spec-Driven Development 反過來：**把規格寫成機器可執行、可驗證的形式**，程式碼只要通過驗證就算「符合規格」。

三種「可執行規格」的形式與本專案的對應：

| 形式 | 本專案的實例 |
|------|--------------|
| **測試即規格** | `test.sh` 的每一條 `assert_*`，例如「POST /enrollments 課程 3 → 回傳 success:true」 |
| **API 範例即規格** | `_doc/plan.md` 的 curl 範例；response JSON 結構 |
| **資料即規格** | `scripts/seed.py --seed 42` 保證假資料可重現，測試永遠建立在已知世界觀上 |

### 本專案例子：一條規格的生命週期

以「重複加選」為例，看它如何從規格一路變成可執行驗證：

1. **需求**（2.2 訪談）：教務處「退了就退，不然紀錄會亂」。
2. **規格**（2.4 表）：`已在 ENROLLED 狀態 → success:false + "您已選修過此課程"`；`已在 DROPPED 狀態 → "已退選課程…"`。
3. **實作**（`enrollment.rs`）：先查既有紀錄，依狀態分支。
4. **可執行驗證**（`frontend/e2e/app.spec.ts:83`）：
   ```ts
   test('重複加選被後端拒絕', async ({ request }) => {
     const first = await request.post(`${API}/enrollments`, { headers, data: { course_id: DUP_COURSE_ID } })
     expect((await first.json()).success).toBe(true)
     const dup = await request.post(`${API}/enrollments`, { headers, data: { course_id: DUP_COURSE_ID } })
     expect((await dup.json()).success).toBe(false)
     expect((await dup.json()).message).toContain('您已選修過此課程')
   })
   ```
5. **規格迷航防線**：如果有人改程式讓重複加選允許成功，這條 E2E 就會紅。

### 版本規格（Milestone Spec）

NQU-ERP 的每一版 `_doc/vX.Y.md` 都是「該版本的規格契約」：列了新增 API、行為、權限、已知限制。例如 `v0.3.1.md` 明確寫「帳號的 `username` 一經建立不可修改」「課程刪除為硬刪除」。**把「不做什麼」也寫進規格**，正是避免第二章 2.1 所說歧義的關鍵。

> **重點**：Spec-Driven Development 的精神是「**規格要有可驗證的判準**」。寫一條需求時問自己：這條需求如果被違反，會有一個測試自動發現嗎？如果不會，它就不是真正被執行的規格。

### 本章練習

1. **規格改寫**：把「學生可以退選」用「條件 + 動作 + 副作用」的格式，寫成一條可測試的規格。
2. **Edge Case 補齊**：針對 `grades` 的三支 API（登錄、送交、查詢），仿照 2.4 的表，各列 3 個 edge case 及你預期的回應。
3. **Red Team 實作**：用 2.5 的 prompt 對「v0.4 選課時程管理（enrollment-period）」做一次紅隊，輸出情境清單並判讀真偽。
4. **規格 vs 程式碼對帳**：`_doc/plan.md` 的 API 表宣稱有 `PUT /admin/enrollment-period`，但 `src/main.rs` 目前沒有。找出「文件—程式碼」的落差，並說明 Spec-Driven 會怎麼處理這種落差。
5. **可執行規格**：在 `test.sh` 中找一條與本章任一 Edge Case 對應的 `assert_*`，寫出它驗證的規格原文。
