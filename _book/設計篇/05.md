# 第五章　測試與品質保證

> 測試不是「寫一支程式來檢查程式」，而是**讓「符合規格」這件事變成可觀察的事實**。本章以 NQU-ERP 的 `test.sh`（後端整合 72 項）、前端 Vitest（26 項）、Playwright E2E（10 項）與 `seed.py --seed 42` 為材料。

---

## 5.1　測試金字塔與測試策略

測試金字塔把測試分成三層，越往下越便宜、越快、越多：

```
        ▲  E2E 少而貴（慢、脆弱、維護難）
      ▲   整合測試 中量（驗證跨模組/跨系統）
    ▲      ｜単元測試 大量（快、像素級、可定位）
```

| 層 | 成本特徵 | 回答的問題 |
|----|----------|------------|
| 單元測試 | 毫秒級、跑整個 JS/Rust 模組 | 這個函式/元件對嗎？ |
| 整合測試 | 秒級、要起 server/DB | 我的 API 在真實 DB 上對嗎？ |
| E2E 測試 | 分鐘級、要開瀏覽器 | 使用者從頭到尾走得通嗎？ |

**策略重點**：金字塔的「形狀」比「總數」重要。全部寫 E2E 會又慢又脆（一個 UI 改版壞整片）；全部寫單元又測不到整合。NQU-ERP 剛好示範了健康形狀的「小型版本」：

| 層 | NQU-ERP | 數量 | 驗證對象 |
|----|---------|------|----------|
| 單元 | Vitest（jsdom）| 26 | 元件邏輯（`UserForm` 編輯模式、`RosterTable`）、純函式 |
| 整合 | `test.sh` 的 API 斷言 | 72 | 完整 REST 行為、權限 403、邊緣情境 |
| E2E | Playwright | 10 | 登入→選課→課表→成績、教師成績、管理員旅程 |

NQU-ERP 後端「全部用整合層來做單元層驗證」是刻意取捨：Rust 端目前沒有單元測試（`cargo test` 為空，`AGENTS.md` 明載），因為 handler 的價值在於「真的跑在 DB 上」，光 mock 起來的花費 > 收益。**測試策略永遠是取捨，不是清單。**

## 5.2　單元測試與 TDD

### TDD（Test-Driven Development）

紅燈 → 綠燈 → 重構：

```
1. 紅燈：先寫一個會失敗的測試（表達你要的行為）
2. 綠燈：寫出讓測試過的最簡單實作
3. 重構：在不改行為下改善結構（第四章 4.2）
```

TDD 的真正產物不是「測試」，而是「**驅動設計**」：先被迫把行為描述清楚，實作自然長得對。

### 本專案例子：把業務邏輯「抽出來」就值得 TDD

整段衝堂判斷是純函式的最佳候選（它不碰 IO，只做區間比較）：

```ts
// 若搬到 src/lib/schedule.ts 就能被吃
export function isOverlapping(a: { day: number; start: number; end: number },
                             b: { day: number; start: number; end: number }): boolean {
  return a.day === b.day && a.start <= b.end && b.start <= a.end
}
```

搭配的 TDD 測試盤：

```ts
test('同一天且區間重疊 → true', () => {
  expect(isOverlapping({ day: 1, start: 6, end: 8 }, { day: 1, start: 3, end: 7 })).toBe(true)
})
test('同一天但完全不相交 → false', () => {
  expect(isOverlapping({ day: 1, start: 1, end: 2 }, { day: 1, start: 3, end: 4 })).toBe(false)
})
test('相接但未重疊 → false', () => {
  expect(isOverlapping({ day: 1, start: 1, end: 3 }, { day: 1, start: 3, end: 4 })).toBe(false)
})
test('不同天 → false', () => {
  expect(isOverlapping({ day: 1, start: 6, end: 8 }, { day: 2, start: 6, end: 8 })).toBe(false)
})
```

這類「邊界案例必須揪出來」的邏輯，是最適合 TDD 的。NQU-ERP 目前把它寫在 Rust handler 的迴圈裡，沒有抽純函式——**這正是「把邏輯抽出去換可測性」的重構建議**（4.2 的延伸）。上面最後一個「相接但未重疊」的測試特別重要：`a.start <= b.end` 用 `<=` 而非 `<`，是區間開閉的語意決定，不寫測試的人幾乎必錯。

前端的 Vitest 26 項主要測的是「元件行為」而非業務純函式：例如 `UserForm` 編輯模式的預填、帳號鎖定、密碼可留空、送出值正確。這是 jsdom 環境下「單元測試」最務實的型態。

## 5.3　整合測試與端到端測試

### 整合測試：test.sh 的工程結構

`test.sh` 是一支指標性的測試腳本，展示了「可執行規格」的紀律（第二章 2.6）。核心是三個斷言函式，刻意設計成**每條失敗都要給出可診斷的訊息**：

```bash
assert_contains() {  # 檢查 body 是否包含某字串
  if echo "$body" | grep -q "$expected"; then PASS=...; else FAIL=...; fi
}
assert_eq() {        # 精確等於
  ...
}
assert_status() {    # HTTP status code
  ...
}
```

執行管線（`test.sh`）本身就是一份 CI 的「在地版」，一旦某一環失敗立刻退出（`set -euo pipefail`）：

```
[0] build        → cargo build
[1] start server → 清空 dev.db、啟動 binary
[2] seed         → seed.py --seed 42 → sqlite3 < seed.sql
[3] health       → GET /health = "OK"
[4] login ...    → 依序打所有 API，逐條 assert
[尾] trap EXIT   → 保證 server 被 kill（不留垃圾 process）
```

**重點**：測試環境必須可重現。清空 DB + 固定 seed + 固定 seed 種子 `42`，保證「同一份測試，今天跑、下週跑、換台機器跑」結果相同——這就是可重現性的工程化（第六章會再提）。

Test 案例的組成（72 項）極度接近第二章的 Edge Case 目錄，例如：

| 測試 | 對應規格/Edge Case | 斷言 |
|------|--------------------|------|
| 非學生加選 403 | 權限邊界 | `assert_status` 403 |
| 重複加選 rejected | 「重複(ENROLLED)」 | body 含「您已選修過此課程」 |
| 退選成功 → count-1 | 副作用 | 查課程的 `enrolled_count` 變回 |
| 教師改他課成績 403 | 身分邊界 | 403「非您授課的課程」 |
| 部署我自己 400 | 身分衝突 | 400「不能刪除自己」 |

### E2E：Playwright 的「真瀏覽器」旅程

E2E 測的是「使用者真的用瀏覽器走得通」。`frontend/e2e/app.spec.ts` 的學生旅程測試：

```ts
test('加選 → 課表與成績 → 退選完整流程', async ({ page }) => {
  await login(page, STUDENT.username, STUDENT.password)
  await page.getByPlaceholder('搜尋課程名稱').fill(COURSE_NAME)
  const card = courseCard(page)
  await card.locator('button', { hasText: '加選' }).click()
  await expect(page.getByText('加選成功！')).toBeVisible()
  await card.locator('button', { hasText: '退選' }).click()
  await page.getByText('退選成功！').waitFor()
})
```

E2E 的脆弱性控制在本專案體現為「E2E 陷阱」紀律（`AGENTS.md` 一整節）：**測試間不能互相污染**。最經典的一條：

> 「退選後不可重選」機制 → 加退選 E2E 各用**獨立課程**（journey 用 course 3，重複加選測試用 course 8），否則「退選」完的課程，下一個測試想「重選」就永遠 400。

其他陷阱（都是踩過才寫下來的規格）：
- `page.addInitScript(localStorage.clear)` 會在每次 goto 重跑導致登出 → 改在 `beforeEach` 先 goto 再 evaluate。
- `getByText` 不分大小寫：`T001` 會命中 `t001@nqu.edu.tw` → 加 `exact: true`。
- 管理員刪除要用 `page.once('dialog', ...)` 處理 `window.confirm`。

**E2E 的哲學**：E2E 不追求多（10 支），只追求「每個角色最重要的一條旅程」被保證。細節交給下層測試。

## 5.4　AI 自動生成測試

### 原理

AI 很會「照規格生成測試案例」，因為測試本質是結構化、可驗證的。但 AI 生成測試有兩個陷阱：

1. **假綠燈（false green）**：AI 生成「看起來有測試、其實沒斷言任何有意義行為」的測試。
2. **與實作共謀**：AI 先看了實作再寫測試，會把實作 bug 寫成「正確期望」。

對策：**先給規格，不給實作**（spec-first testing），並要求每個測試都寫「為什麼這個案例重要」。

### 本專案例子：讓 AI 依規格生成測試

**Prompt（spec-first）：**

```
請為「學生退選」API（DELETE /api/v1/enrollments）生成整合測試案例。
只允許參考這份規格，不要看實作：
- 輸入：course_id
- 成功條件：選課紀錄狀態 ENROLLED → 改為 DROPPED，enrolled_count - 1，刪除對應成績
- 邊界：未選過的課 404；已 DROPPED 的課 404（「未找到選課紀錄」）；
       非學生身分 403；名額為 0 時不該往下扣
請每條案例寫明：準備的狀態 → 動作 → 斷言。
```

**AI 產出的樣貌（節錄）與人審查：**

| AI 案例 | 審查判斷 |
|---------|----------|
| 「選課 3 次再退 3 次，enrolled_count 正確」| ✅ 好，覆蓋有狀態累積的情境 |
| 「退選後 enrolled_count 不減為負」| ⚠️ 值得留——但實作已用 `if course.enrolled_count > 0` 防呆，這測試是在驗證防呆 |
| 「非學生退選 403」| ✅ 好（對 2.4 權限表）|
| 「assert 回應 body 含『退選成功』」| ⚠️ 太脆——中文 substring 若排版改變就誤報，改用 status 或結構欄位 |

AI 生成測試的最大價值是**「覆蓋率的提議」**：它指出「你沒測到退 DROPPED 的課」時，激發人想起這條規則。最大風險是假綠燈，所以審查重點是**「斷言到底鎖住了什麼行為」**。

## 5.5　LLM-as-a-Judge：用模型評判模型

### 原理

LLM-as-a-Judge（用 LLM 當裁判）是 AI 時代新的品質槓桿：**用一個模型去評判另一段文字/程式/輸出**。用在軟體工程上：

1. **測試品質評分**：審判一組測試是否真的測到規格（rubric 給分）。
2. **錯誤訊息評分**：評「這條錯誤訊息能不能讓使用者行動」。
3. **程式碼審查摘要**：LLM 讀完 diff，產出「變更意圖 vs 變更內容」對帳單，加速人審。
4. **測試生成再過濾**：LLM 給每個生成的測試案例評分，只留高分的進測試庫。

關鍵成功條件：

| 條件 | 說明 |
|------|------|
| **清楚的 rubric（評分表）** | 「訊息是否包含『具體課程的衝突節次』」是可機械判讀的，比「訊息好不好」可靠 |
| **獨立證據** | Judge 應該只能看規格 + 被審的產物，不能看被審程式的實作 |
| **calibration（校準）** | LLM 評分常偏高（過度自信），要人工抽樣校準 |
| **人保留最終決定權** | Judge 是「排序/提議」工具，不是自動 merge 的蓋章機 |

### 本專案例子：用 Judge 審「錯誤訊息」

對 `enroll_course` 的兩條候選訊息用 rubric 評分：

```
Rubric（0–3）：
- 是否指出「哪個條件失敗」？（名稱/節次/名額）
- 是否指出「下一步該做什麼」？
- 是否與專案既有訊息風格一致（中文、精確）？

訊息A：「課程時間衝突！與已選課程在星期 1 第 6~8 節重疊」
  → 得分 3：精確節次（可行動）＋中文風格一致。

訊息B：「參數錯誤」                      
  → 得分 0：無法行動。
```

Judge 的價值：可以批處理幾十條候選訊息、產出一致的排序，人只要人工複核高分群。**這把「訊息品質」也變成了一套可被評分、可改進的規格**——等於把 2.4「錯誤訊息品質本身是需求」這句話自動化。

> 警告：Judge 對於「事實性的正確性」判斷力有限。判斷「衝堂條件寫對沒」這種事，仍要依靠傳統測試（`assert`）。**LLM-as-a-Judge 用在「品質/風格的評分」，傳統測試用在天人合一的「行為正確性」。**

## 5.6　迴歸測試與持續驗證

迴歸測試（Regression Testing）的目的是：**每次改版後，過去修好的 bug 不會復活**。NQU-ERP 的做法極具示範性——**把品質關卡寫進 AGENTS.md，當成不可協商的紀律**：

```bash
cargo fmt && cargo clippy && cargo build && bash test.sh
cd frontend && bash test.sh
```

### 版本 = 迴歸池的成長史

從 `_doc/` 的歷史可以看到「每修一個 bug 就回填一筆測試」的證據（測試數就是迴歸池的成長史）：

| 版本 | 後端測試數 | 新增了什麼類型的迴歸防護 |
|------|-----------|--------------------------|
| v0.1 | 33 | 基本 API 各一支 |
| v0.3 | 48 | 名冊、管理列表、權限 403 共 15 項 |
| v0.3.1 | 72 | 改名生效、舊密碼失效、防刪保護 400、重複刪除 404 等 24 項 |

v0.3.1 的例子最能說明迴歸價值：新增「修改帳號」功能後，UI 有「密碼留空＝不變」的規則。若沒有測試鎖住「留空密碼不會意外重設」，之後任何人改 `update_user` 都可能把使用者密碼清掉——這是一個**看不見的 bug，只有迴歸測試抓得到**的工具。

### 持續驗證的流程設計

`frontend/test.sh` 展示了「E2E 前的環境重置」紀律：

```
build → 起後端（輪詢 /health）→ seed(42) → 驗證 courses = 15
     → Vitest → Playwright E2E
E2E 前會重置 dev.db，用後需手動 git checkout dev.db 或重跑 seed
```

為什麼要「驗證 courses = 15」？因為如果 seed 失敗，後面 E2E 會錯得莫名其妙——**先把環境錯誤擋在前面，讓後續錯誤訊息有意義**。這是測試工程裡「前置條件快速失敗」的典型。

### 本章練習

1. **純函式重構 + TDD**：把衝堂判斷抽成 `isOverlapping`（5.2 的版本），先在 `frontend/src/__tests__/schedule.test.ts` 寫紅燈測試，再實作轉綠。
2. **新增迴歸測試**：在 `test.sh` 中新增「退選後重選被拒」的斷言（用 course 8，避免污染），並說明代價。
3. **測試金字塔審查**：本書列了三層的數量，試著「砍掉一半 E2E」判斷風險，或「把一半整合升級成 E2E」判斷成本。
4. **LLM-as-a-Judge 實作**：用 5.5 的 rubric，找專案三句中文錯誤訊息，為每一句打 0–3 分，並提出改版建議。
5. **假綠燈偵測**：故意寫一支「看起來對、其實沒鎖住行為」的測試（例如斷言 `success:true` 但不檢查名字額），用 5.4 的方法與人討論它為何是假綠燈。
