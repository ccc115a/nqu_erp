# 第三章　系統設計

> 需求決定「做什麼」，設計決定「怎麼拆」。本章談抽象、模組化、架構模式與 API 設計，並以 NQU-ERP 的 `src/main.rs`（路由）、`src/middleware/auth.rs`（認證）與前端 `api/client.ts` 為例。

## 3.1　設計思維：抽象、模組化與資訊隱藏

三個核心概念：

1. **抽象（Abstraction）**：忽略不相關細節，只保留對當前目的重要的部分。
2. **模組化（Modularity）**：把系統切成可獨立開發、測試、替換的單元。
3. **資訊隱藏（Information Hiding）**：模組的內在實現細節不讓外界看見，外界只能透過「介面」使用它。改了實作，呼叫端不需跟著改。

判別設計好壞的常用問句：**「如果我改掉 A 的內部實作，B 需要跟著改嗎？」** 答案若是「不需要」，A 就封裝得當。

### 本專案例子：一個藏得特別好的抽象——DB 抽換

`config.rs` 把資料庫 URL 變成一個字串設定：

```rust
database_url: env::var("DATABASE_URL")
    .unwrap_or_else(|_| "sqlite://dev.db?mode=rwc".into()),
```

`db.rs` 用 `sea_orm::Database::connect(&database_url)` 建立連線；**同一個程式**在開發環境吃 SQLite、在生產環境吃 PostgreSQL，一行程式碼都不用改。背後的機制是：

- **Entities 抽象**：`entities/*.rs` 把資料表描述成結構，不綁定某個 DB dialect。
- **SeaQuery 抽象**：查詢建立器幫你翻譯 `?` vs `$1`、`RETURNING` 等方言差異。
- **Migration 抽象**：schema 的建立也是資料庫無關的程式碼。

於是一旦要把 SQLite 換成 PostgreSQL，改的是「設定」而不是「程式碼」——這就是**抽象讓系統可替換**的直接證據。

### 本專案例子：模組化反映在檔案邊界

`src/` 的切法本身就是設計決策：

| 目錄 | 職責 | 外界（其他模組）看到的是 |
|------|------|--------------------------|
| `handlers/*` | HTTP 進出的業務邏輯 | 每個 handler 函式的簽名 |
| `entities/*` | 資料模型與關聯 | SeaORM Entity |
| `middleware/auth.rs` | 認證與角色 | `AuthUser` 型別 |
| `errors.rs` | 錯誤的統一形狀 | `AppError` |
| `config.rs` | 環境設定 | `Config` |

一個 handler 壞了，錯誤冒泡到 `errors.rs` 被統一拍版成 JSON；呼叫端不需要知道內部細節。資訊隱藏也保證了第四章要談的「重構安全」。

## 3.2　架構模式：從單體到微服務

架構模式的頻譜：

```
單體（Monolith） ──► 模組單體 ──► 微服務（Microservices）
   簡單、成本低         適度切分          獨立部署、可擴展但分散式昂貴
```

**關鍵認知**：微服務不是「比較先進」，而是「代價換收益」的取捨。分散式系統要付的帳：網路延遲、部分失敗（partial failure）、最終一致性、分散式追蹤、部署複雜度。對多數中小型系統，**模組化單體（modular monolith）**才是最划算的起點。

### 本專案例子：NQU-ERP 是一個「模組化單體」

NQU-ERP 全部跑在一個 process（`axum::serve`）裡，但內部切分整齊──正是模組化單體：

```rust
let app = Router::new()
    .route("/health", get(|| async { "OK" }))
    .route("/api/v1/auth/login", post(handlers::auth::login))
    .route("/api/v1/courses", get(handlers::course::list_courses))
    .route("/api/v1/enrollments",
        post(handlers::enrollment::enroll_course)
            .delete(handlers::enrollment::drop_course))
    // ...
    .with_state(state)
    .layer(cors);
```

任何「模組」要變成獨立服務，成本很低：`handlers::enrollment` 依賴的只有 `AppState`（DB + JWT secret）與 `AuthUser`，介面清楚。但現在的設計**不**微服務化是正確的決定，原因：

1. 沒有獨立擴展的需求（選課高峰可用加機器解決，但那是第 6 章的事）。
2. 轉移一次成本（Transaction、Join、遷移）在分散式下變成極貴。
3. 單一測試流程簡單：`test.sh` 一個 server 就能全測。

> **設計教訓**：先做好「模組化」，把「是否拆成服務」留到規模證據出現之後再決定。Book 的 6.1 會用 CI/CD 討論拆服務的版圖。

## 3.3　API 與介面設計（ACI vs HCI）

圖靈測試之後，AI 時代的介面設計出現一個新分類：

- **HCI（Human-Computer Interaction）**：人看的介面。按鈕、表單、訊息。
- **ACI（Agent-Computer Interaction）**：**AI Agent 看的介面**。Agent 會用程式化方式呼叫你的 API、解析你的 JSON、讀你的錯誤訊息。

好的 API 設計必須**同時服務兩種文明**：給人看要一致、好讀、有中文可操作訊息；給 Agent 看要結構穩定、錯誤可分型、欄位語意明確。因為現在「下一個消費者」很可能是程式（前端 axios）或 AI（自動化 agent），不是人類。

### 本專案例子：成功的 API 設計系統

NQU-ERP 的先驅成果在於**非常一致的介面契約**。以 `errors.rs` 為例：

```rust
impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let body = json!({ "error": self.message, });
        (self.status, axum::Json(body)).into_response()
    }
}
```

**所有失敗**都長這樣：`{ "error": "..." }` + 正確的 HTTP status code。成功則統一 `{ success: true, message }`（或直接回資料陣列）。這對兩種消費者都極友善：

| 消費者 | 為何好 |
|--------|--------|
| 前端（人）| `getErrorMessage(err)` 直接取 `data.error` 顯示，中文訊息可讀 |
| AI Agent | 錯誤統一結構 + status code → 可以寫 `if 403 → 換角色；if 404 → 查一下對象是否存在` 的處理邏輯 |

**A偏 C 設計的關鍵守則**（以本專案驗證）：

1. **用 HTTP 語意**：403 是權限、404 是不存在、400 是業務拒絕——Agent 光看 status 就能分診。
2. **訊息要可行動（actionable）**：比起 `"error": "bad request"`，`"課程時間衝突！與已選課程在星期 1 第 6~8 節重疊"` 才能讓使用者/Agent 據此處理。
3. **DTO 是對外契約**：`EnrollResponse`、`CourseItem` 等結構明確定義只有要揭露的欄位，不會順手把 password_hash 外洩（資訊隱藏在 API 層的體現）。
4. **REST 語意對齊需求**：`POST /enrollments` 加選、`DELETE /enrollments` 退選、`PUT /grades/batch` 整批寫入——路徑/動詞本身就說明意圖。

前端 `api/client.ts` 正是 HCI 與 ACI 的交匯點：一個 axios 攔截器，幫所有頁面統一夾帶 `Bearer` token，401 自動登出──**介面一致性的實現，不只靠後端，也靠前端單一出口**。

## 3.4　設計原則：SOLID、DRY 與 KISS

### SOLID 逐條對照本專案

| 原則 | 意義 | NQU-ERP 證據 |
|------|------|--------------|
| **S** 單一職責 | 一個型別/函式只做一件事 | 每個 handler 一職責一檔案；`errors.rs` 只做錯誤形狀；`config.rs` 只做設定 |
| **O** 開放封閉 | 對擴展開放、對修改封閉 | 新增角色→新增一個 `is_xxx()` 判斷即可，不改授權機制；新增 handler→在 `Router` 加一行 `.route`，不動舊 handler |
| **L** 里氏替換 | 子型別/實作可安全替換基底 | `AuthUser` 的 `FromRequestParts<AppState>` 讓所有 handler 用同一個取用方式，換 JWT 實作只動一個檔案 |
| **I** 介面隔離 | 客戶端不依賴它不用的東西 | 每個 handler 宣告自己的最小 DTO（`EnrollRequest` 只有 `course_id`），不會把整張表塞給客戶端 |
| **D** 依賴反轉 | 高層依賴抽象而非實作 | Handler 依賴 `DatabaseConnection` 與 `EntityTrait`，不依賴具體 DB driver；換 DB 只改設定 |

### DRY（Don't Repeat Yourself）

DRY 的目的不是「少打字」，而是「**單一事實來源（Single Source of Truth）**」。重複的知識沒收斂，改一處漏一處。

NQU-ERP 的收斂範例：

- **錯誤統一**：所有 403 都是 `AppError::forbidden("...")`，錯誤包裝只寫在 `errors.rs` 一處。
- **認證收斂**：`AuthUser` extractor 讓每個 handler 不必重寫「抓 Authorization header → decode JWT」的步驟；`api/client.ts` 的 interceptor 讓每個前端頁面不必重寫夾 token。
- **權限名詞收斂**：`is_student()/is_teacher()/is_admin()` 替代散落的 `role == "STUDENT"` 字串比較。

反例（DRY 待改善）：`list_courses` 與 `get_teacher_courses` 幾乎是同一份「組 CourseItem」的迴圈，`grade.rs` 的多支 handler 也有要拉到共用 helper 的潛力——這正是第四章 4.2 重構的候選人。

### KISS（Keep It Simple, Stupid）

NQU-ERP 的簡單決定：

- 單體而不是微服務（3.2）。
- 查詢參數用 `HashMap<String, String>` 直接取，不做過度的 query-param 框架（`course.rs:36`）。
- `grades/submit` 用簡單迴圈逐筆 update，不為了「優雅」引入複雜的批次 SQL。
- 沒有引入超過需求的 Redis、訊息佇列（`_doc/plan.md` 把它們標成「後期優化/Future」）。

KISS 的判斷標準：**如果一個簡化不會造成未來明確的痛，就選簡化**。

## 3.5　AI 時代的系統設計：高內聚低耦合的新意義

### 原理

「高內聚、低耦合」在 AI 協作時代有了新意義：**耦合不只是程式碼層面的，是「可理解性與可改動性的邊界」**。當 AI（或新同事）要修改一個模組時：

- **高內聚** = 這個模組的相關知識都在一起，AI 讀 `enrollment.rs` 一個檔就能理解整條加選流程，不需要東拼西湊。
- **低耦合** = 改 `enrollment.rs` 不需要同時改 `grade.rs`、`course.rs`、前端三個頁面。模組間的接觸面是**穩定的契約**（API 形狀、DTO、錯誤訊息）。

AI 時代設計的新原則：**「能不能讓修改被安全地驗證」**。如果每個模組有清楚的入口與出口，AI 改完可以只跑相關測試驗收；如果模組互相藕斷絲連，AI 改 A 就得擔心 B、C、D 跟著壞，AI 的可靠性就大幅下降。

### 本專案例子：設計一個「AI 友善」的模組

以 `handlers/enrollment.rs` 為例，分析它為什麼「AI 友善」：

| 設計特徵 | 對 AI 協作者的好處 |
|----------|--------------------|
| **單一流程在同一個檔**：`enroll_course` 從權限檢查→重複檢查→衝堂→名額→寫入→commit 依序展開 | 讀一個文件就能理解整條業務路徑，不用跳檔 |
| **型別即文件**：`EnrollRequest` / `EnrollResponse` 定義了輸入輸出 | AI 只要看型別就知道要接什麼、回什麼 |
| **錯誤全走 `AppError`** | AI 可以預測「這裡該回 4xx 的哪一個」 |
| **命名對齊業務**：`enrolled_count`、`is_submitted` | AI 從欄位名就能推測語意，減少誤解 |
| **測試即行為規格**：`test.sh` 與 `e2e/` | AI 改完有明確的「綠燈」標準 |

**設計準則的具體化（AI 時代版本）**：

1. 把「知識」放在一起（內聚），把「變動」隔離開（低耦合）。
2. 讓邊界介面（API/型別/錯誤）盡可能**自描述**，減少默契（tacit knowledge）。
3. 替每個模組留一條「可獨立驗證的路徑」——至少有一個測試只依賴它的公開契約。
4. 對 AI 生成程式碼的態度：**同一個人類評審，會更信任「耦合低、出口清楚」的模組**。設計上讓模組保持「小而完整」。

> **本章總結**：設計的終極目標不是「精美的圖」，而是「**把變動的爆炸半徑壓到最小，把可驗證性放到最大**」。這個目標在 AI 時代比過去任何時候都更明確。

### 本章練習

1. **資訊隱藏檢查**：`entities/` 有沒有可能被 handler 以外的程式直接修改內部結構？查 `src/entities` 的可見性（`pub`）設計，說明哪一處違反了資訊隱藏。
2. **API 契約表**：為「教師成績登錄」畫一張表格：HTTP method、路徑、輸入 JSON、成功輸出、各失敗 status 與訊息（參考 `grade.rs`）。
3. **SOLID 檢討**：`grades/submit`（`grade.rs:101`）目前沒有「確認教師是該課程授課者」的檢查（只有角色檢查）。用 DIP/資訊隱藏的角度討論此缺口，並提出修正。
4. **ACI 設計**：假設要讓一個 AI Agent 自動完成「幫某學生加選課程」，寫出它呼叫 API 的流程，並指出目前的 API 契約會在哪一步造成 Agent 需要「猜」。
5. **高內聚低耦合實測**：統計「修改一處領域規則」會牽動幾個檔案。例如把「退選後可重選」改回允許，列出需要動的程式碼位置（後端幾處、前端幾處、測試幾處）。
