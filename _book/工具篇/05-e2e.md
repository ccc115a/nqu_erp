# 第五章　Playwright：端到端測試詳解

> 本章以 `frontend/e2e/app.spec.ts`（10 項）為全文教材。讀者應先跑過 `npx playwright test`。本章把每一類測試拆開講：設定、登入、旅程、API 混合、動態標的、刪除確認。

---

## 5.1　E2E 在測試金字塔的位置

### 原理

E2E（端到端）用**真瀏覽器**從使用者入口走完整條路：開頁 → 登入 → 點按鈕 → 看結果。它最貴（慢、脆弱），所以只保「**每個角色最重要的一條旅程**」，細節交給下層（第 3、4 章）。

NQU-ERP 的分工：

| 層 | 工具 | 數量 | 保什麼 |
|----|------|------|--------|
| 單元 | Vitest | 26 | 元件與純函式 |
| 整合 | `test.sh` | 72 | API 行為與邊界 |
| E2E | Playwright | 10 | 學生旅程、教師送交、管理員增修刪 |

10 項的組成：學生 7（導向、錯密、教師導向、搜尋、加退選旅程、重複加選、登出）+ 教師 1（登錄鎖定）+ 管理員 2（帳號增修刪、課程增修刪）。

## 5.2　設定檔與測試前準備

`playwright.config.ts`（節錄）：

```ts
export default defineConfig({
  testDir: './e2e',
  fullyParallel: false,
  workers: 1,          // 單執行緒：測試共享同一份 DB 狀態，不可並行
  retries: 0,
  use: { baseURL: 'http://localhost:5173' },
  webServer: {
    command: 'npm run dev -- --port 5173 --strictPort',
    url: 'http://localhost:5173',
    reuseExistingServer: true,
  },
})
```

三個關鍵決定都有理由：`workers: 1` 是因為「退選後不可重選」——並行跑會互相污染（5.5 節）；`reuseExistingServer: true` 讓本地已起的 Vite 可被重用；`baseURL` 讓 `page.goto('/login')` 寫相對路徑。

每個測試前的清場（全文第一段，必讀）：

```ts
test.beforeEach(async ({ page }) => {
  await page.goto('/login')
  await page.evaluate(() => localStorage.clear())
})
```

為什麼不寫在 `addInitScript`？因為那會在**每次** `goto` 重跑清掉 token，把登入者登出（`AGENTS.md` 明列）。正確順序是「先到登入頁、再清一次」——**順序本身就是規格**。

共用 helper（登入 + 卡片定位）：

```ts
async function login(page: Page, username: string, password: string) {
  await page.goto('/login')
  await page.getByPlaceholder('學號').fill(username)
  await page.getByPlaceholder('密碼').fill(password)
  await page.getByRole('button', { name: '登入' }).click()
}

function courseCard(page: Page) {
  return page.locator('.rounded-lg.border', { hasText: COURSE_NAME })
}
```

`courseCard` 鎖住的是**前端 DOM 契約**：課程卡片永遠是 `.rounded-lg.border`。改版若換掉這個 class，E2E 會紅——這是 E2E 脆弱性的來源，也是它的價值（改 UI 要有意識）。

## 5.3　範例一：學生完整旅程（加選→課表→成績→退選）

這是 10 項中最重要的一支，全文：

```ts
test('加選 → 課表與成績 → 退選完整流程', async ({ page }) => {
  await login(page, STUDENT.username, STUDENT.password)
  await page.waitForURL('**/courses')

  await page.getByPlaceholder('搜尋課程名稱').fill(COURSE_NAME)
  const card = courseCard(page)
  await expect(card).toBeVisible()

  // 加選後應出現「已選修」狀態（退選按鈕）
  await card.locator('button', { hasText: '加選' }).click()
  await expect(page.getByText('加選成功！')).toBeVisible()
  await expect(card.locator('button', { hasText: '退選' })).toBeVisible()

  // 我的課表應顯示該課程
  await page.getByRole('link', { name: '我的課表' }).click()
  await expect(page.getByText(COURSE_NAME)).toBeVisible()

  // 我的成績應顯示預設修課紀錄
  await page.getByRole('link', { name: '我的成績' }).click()
  await expect(page.getByText('我的成績')).toBeVisible()
  await expect(page.getByText('資料結構')).toBeVisible()

  // 回課程瀏覽並退選，還原測試前狀態
  await page.getByRole('link', { name: '課程瀏覽' }).click()
  await page.getByPlaceholder('搜尋課程名稱').fill(COURSE_NAME)
  await courseCard(page).locator('button', { hasText: '退選' }).click()
  await page.getByText('退選成功！').waitFor()
})
```

讀法（四段式旅程）：

1. **登入與搜尋**：`waitForURL('**/courses')` 確認角色導向正確（學生首頁），再搜尋 `計算機網路`（`COURSE_ID = 3`）。
2. **加選**：按卡片上的「加選」，斷言中文「加選成功！」+ 按鈕翻成「退選」。
3. **跨頁驗證**：課表頁看得到課、成績頁看得到紀錄——**同一份後端狀態在三個頁面一致**，這是單元測不到的。
4. **還原**：退選把狀態清回去。E2E 的禮貌：**測試結束時世界要和開始時一樣**，否則下一個測試遭殃。

## 5.4　範例二：API 混合測試（重複加選）

不是每件事都要開瀏覽器點。用 `request` fixture 直接打 API 又快又穩：

```ts
test('重複加選被後端拒絕', async ({ request }) => {
  const token = await studentToken(request)
  const headers = { Authorization: `Bearer ${token}` }

  const first = await request.post(`${API}/enrollments`, { headers, data: { course_id: DUP_COURSE_ID } })
  expect((await first.json()).success).toBe(true)

  const dup = await request.post(`${API}/enrollments`, { headers, data: { course_id: DUP_COURSE_ID } })
  expect((await dup.json()).success).toBe(false)
  expect((await dup.json()).message).toContain('您已選修過此課程')

  await request.delete(`${API}/enrollments`, { headers, data: { course_id: DUP_COURSE_ID } })
})
```

三個細節都是實戰結晶：

- `studentToken()` 先打 `POST /auth/login` 拿 token——E2E 也要測「登入發得出 token」這條鏈。
- `Authorization` 要手動加 `Bearer ` 前綴（Playwright 不像 axios interceptor 自動夾，`AGENTS.md` 明列）。
- 用 `DUP_COURSE_ID = 8` 而**不用**旅程的 course 3——因為旅程已把 course 3 加選又退選，而「退選後不可重選」，共用會永遠 400。**測試間的狀態隔離要用「獨立資料」實現**，這是本專案最重要的 E2E 紀律。

## 5.5　範例三：動態標的（教師成績鎖定）

教師測試不能寫死「改某學生的成績」——seed 重跑或別人先送交，寫死的標的可能已鎖定。解法：**測試開始時用 API 現場找一個未送交的學生**：

```ts
async function teacherGradeTarget(request: APIRequestContext) {
  const token = await teacherToken(request)
  const headers = { Authorization: `Bearer ${token}` }
  const courses = (await (await request.get(`${API}/teachers/me/courses`, { headers })).json())
  for (const c of courses) {
    const roster = (await (await request.get(
      `${API}/teachers/me/courses/${c.course_id}/students`, { headers })).json())
    const target = roster.find((r) => !r.is_submitted)
    if (target) return { courseId: c.course_id, studentNumber: target.student_number }
  }
  throw new Error('no unsubmitted roster found in seed')
}
```

拿到標的後才開瀏覽器操作：

```ts
await page.goto(`/teacher/courses/${target.courseId}`)
const midInput = page.getByLabel(`期中考 ${target.studentNumber}`)
await midInput.fill('88')
await page.getByRole('button', { name: '儲存成績' }).click()
await expect(page.getByText('成績登錄成功')).toBeVisible()

await page.getByRole('button', { name: '鎖定送交' }).click()
await expect(page.getByText('確認鎖定送交？')).toBeVisible()
await page.getByRole('button', { name: '確認送交' }).click()
await expect(page.getByText('成績已鎖定送交')).toBeVisible()
await expect(page.getByLabel(`期中考 ${target.studentNumber}`)).toBeDisabled()
```

`getByLabel('期中考 {學號}')` 與第 4 章的 `getByLabelText` 是同一個 `aria-label` 契約——**可測試性設計一次，單元與 E2E 共享**。最後一行 `toBeDisabled()` 把「送交即鎖定」釘死在瀏覽器層。

## 5.6　範例四：管理員刪除（dialog 與精確匹配）

刪除有兩個 Playwright 經典坑，本專案全踩過：

```ts
// 精確匹配：T001 不該命中 t001@nqu.edu.tw
await expect(page.getByRole('cell', { name: 'T001', exact: true })).toBeVisible()
// 精確匹配：『姓名』不該命中『搜尋帳號 / 姓名 / 角色』
await page.getByPlaceholder('姓名', { exact: true }).fill('測試新生')

// window.confirm 要在 dialog 事件裡接受，否則卡死
page.once('dialog', (dialog) => dialog.accept())
await page.getByRole('row', { name: /測試改名/ }).getByRole('button', { name: '刪除' }).click()
await expect(page.getByText('刪除成功')).toBeVisible()
await expect(page.getByRole('row', { name: /測試改名/ })).toHaveCount(0)
```

| 坑 | 原因 | 解法 |
|----|------|------|
| 大小寫不敏感匹配 | `getByText('T001')` 會命中信箱 `t001@…` | 一律 `exact: true` |
| placeholder 前綴匹配 | `姓名` 命中搜尋框的 placeholder | 同樣 `exact: true` |
| `window.confirm` 卡住 | 不處理 dialog，測試懸掛逾時 | 先 `page.once('dialog', accept)` 再按刪除 |
| 訊息中夾帳號 | 「帳號 S099 刪除成功」全文斷言太脆 | 斷言 substring `刪除成功` |

> **重點**：5.3–5.6 的每一條「怪規矩」背後都是一次真實失敗。`AGENTS.md` 的「E2E 陷阱」就是這樣攢出來的——**E2E 的知識管理，本身就是測試工程的一半**。

#### 練習 3　讀旅程：追一遍「密碼錯誤」測試的斷言鏈

目標：學會讀 E2E 的「斷言鏈」——從 UI 字串一路追到後端錯誤。

步驟（不需跑環境，讀程式即可）：

```bash
sed -n '39,45p' frontend/e2e/app.spec.ts   # 密碼錯誤那支
grep -rn "帳號或密碼錯誤" src/ frontend/src --include="*.rs" --include="*.ts*" | head -5
```

預期結果：你會看到一條完整的鏈——E2E 斷言頁面出現「帳號或密碼錯誤」→ 來自後端 `auth.rs` 的 `AppError::unauthorized("帳號或密碼錯誤")` → 經 `api/client.ts` 的 `getErrorMessage` 透出（工具篇 04 練習的 `client.test.ts` 第一支測的正是它）→ 顯示在登入頁。

接著回答：若要為「帳號不存在」補一支邊界測試，該怎麼寫？（提示：仿 39–45 行，把密碼改成不存在的學號，斷言同一句中文——因為後端對「帳號錯」與「密碼錯」回同一訊息，避免帳號枚舉攻擊。）

觀察：**一條 E2E 串起三層**（後端訊息 → 前端透出 → 頁面顯示）。這就是 E2E 存在的理由：單層測試全綠，三層接起來仍可能斷（例如 interceptor 忘了透出 `error` 欄位）。

#### 練習 5　動態標的：讓 `teacherGradeTarget` 更強壯

目標：理解「寫死標的」vs「動態找標的」的取捨，並動手改進。

步驟：

```bash
sed -n '218,233p' frontend/e2e/app.spec.ts   # 看原版 teacherGradeTarget
```

原版用 `roster.find((r) => !r.is_submitted)` 取第一個未送交學生。思考它的脆弱性：如果該課程只有 1 位未送交學生，而你的測試把它送交鎖定了，下一個要測「登錄未送交」的測試（或重跑同一支）就找不到標的 → `throw new Error('no unsubmitted roster found')`。

動手改（練習用，改完可保留或還原）：

```ts
// 改成：找「有 ≥2 位未送交學生」的課程，回傳前兩位
const targets = roster.filter((r) => !r.is_submitted)
if (targets.length >= 2) return { courseId: c.course_id, students: targets.slice(0, 2) }
```

```bash
npx playwright test -g "登錄成績並鎖定送交" 2>&1 | tail -4
# 注意：此測試會真的送交鎖定一個學生的成績，跑完後 seed 變髒。
# 還原：sqlite3 ../dev.db < ../scripts/seed.sql（或重跑前置作業的 seed 兩行）
```

觀察：動態標的是 E2E 的進階技巧——**測試自己找测試資料**，不依賴寫死的 id。但它有代價：測試會「消耗」標的（送交即鎖定），所以跑完要還原 seed。記住這條：**會寫入的 E2E，結尾都要有還原**（5.3 旅程的退選、5.4 的 delete，都是同一條紀律）。
