# 第四章　程式設計與實作

> 前兩章把「什麼」與「怎麼拆」講完了，本章談「真的把程式寫好」。以 NQU-ERP 的實際程式碼、`AGENTS.md` 的工作紀律與 git 歷史為材料。

## 4.1　程式碼品質與可讀性

可讀性不是「喜歡與否」的風格問題，而是**經濟問題**：程式被讀的次數遠多於被寫的次數，讀起來越慢，維護成本越高。可讀性的幾個指標：

1. **命名精確**：變數名稱本身就是註解。
2. **函式短**：一個函式講一件事（對齊 3.4 的 SRP）。
3. **空行與段落的節奏**：像文章分段一樣把「步驟」分開。
4. **少即多**：不必要的註解與死碼是雜訊。
5. **型別當文件**：強型別語言用型別表達意圖。

### 本專案例子：命名即文件

`enrollment.rs` 的衝堂演算法，讀起來像在讀校務規則：

```rust
if cs.day_of_week == ts.day_of_week
    && cs.start_period <= ts.end_period
    && ts.start_period <= cs.end_period
```

`cs`（current schedule）跟 `ts`（target schedule）命名短，但配合完整的 `current_schedules` / `target_schedules` 變數，意圖一目了然。又例如 DTO：

```rust
pub struct DropRequest { pub course_id: i32 }
```

「退選就是交一個 course_id」，介面自己會說話。

**「不加不必要的 comments」**（見 `AGENTS.md`）是本專案的明文紀律：程式應該自我說明，只有當「為什麼」無法從程式碼看出時才寫註解。品質關卡是機械化的──`cargo fmt && cargo clippy`（零警告）與後端 build，把「風格」與「明顯錯誤」交給工具，人專注在語意。

### 中文錯誤訊息也是一種可讀性設計

業務錯誤全部使用中文（「帳號或密碼錯誤」），不是為了「語言喜好」，而是：**錯誤訊息的最終消費者是用戶**，訊息要能直接幫助使用者行動（3.3 的 actionable 原則）。若訊息寫成技術術語，使用者無法處理，客服就會被打爆。

## 4.2　重構：改善既有設計的藝術

重構（Refactoring）＝**不改變外部行為的前提下，改善內部結構**。鐵則：**每次重構都是一小步 + 一次測試確認**，不是大爆炸式的重寫。

重構的兩個支撐：

1. **安全網**：一支快速測試告訴你這一步沒改壞行為（第五章會講這套安全網在 NQU-ERP 長什麼樣）。
2. **嗅覺**：聞到壞味道（duplicate、long method、feature envy）才動手。

### 本專案例子：一處可安全進行的重構

`course.rs` 的 `list_courses` 與 `get_teacher_courses` 共用同一段「把 course → CourseItem」的組裝邏輯（teacher、dept、schedules 的查詢與 mapping）。壞味道：**Duplicate 迴圈**。

重構步驟（在學堂上可以現場示範）：

```rust
// Refactor 1：抽出共用組裝
async fn build_course_items(state: &AppState, courses: Vec<Course>) -> Result<Vec<CourseItem>, AppError> {
    let mut items = Vec::new();
    for c in courses {
        let teacher = users::Entity::find_by_id(c.teacher_id).one(&state.db).await?;
        let dept = departments::Entity::find_by_id(c.dept_id).one(&state.db).await?;
        let schedules = class_schedules::Entity::find()
            .filter(class_schedules::Column::CourseId.eq(c.course_id)).all(&state.db).await?;
        items.push(/* map 成 CourseItem */);
    }
    Ok(items)
}
```

`get_teacher_courses` 原本還多查一個 dept，重構後也一併統一。**行為不變**的驗證：`test.sh` 中既有課程列表與教師授課清單的斷言全部原樣通過。

另一處重構候選：`grades/submit` 的行為可被改成「**先驗證該課是本人的課再加鎖**」──這同時修掉 3.5 練習提到的授權缺口，屬於「重構夾帶 bug fix」的正確時機。

> **重構關鍵心法**：重構時 **「像貓一樣，一次只動一隻腳」**——`fmt`、抽出函式、改型別，每一步都跑測試。安全網存在，重構就只是時間問題；安全網不存在，要先補網再動手。

## 4.3　設計模式的實用指南

設計模式是「**反覆出現的結構性問題，被驗證過的解法**」。但關鍵在「實用」二字：**模式是為了解決真實痛點，不是裝飾**。過度套用模式，程式會充滿抽象而失去可讀性（違反 KISS）。

### 本專案例子：NQU-ERP 實際用到的模式

| 模式 | nominal 定義 | 在本專案的實際用法 |
|------|--------------|--------------------|
| **Extractor（Context）** | 跨請求共享的環境/身分，注入到 handler | `AuthUser` 實作 `FromRequestParts<AppState>`，從 Authorization header 解出使用者身分，所有 handler 直接宣告 `auth: AuthUser` 就拿得到 |
| **Transaction（Unit of Work）** | 一組操作要嘛全成功要嘛全不發生 | `enroll_course`：重複檢查→衝堂→名額→寫入→commit，單一交易包住；`delete_course` 用交易清掉關聯資料 |
| **DTO（Data Transfer Object）** | 邊界上的資料傳輸結構，隔離內外模型 | `CourseItem`、`RosterItem`、`StudentGradeItem` 只揭露該角色需要的欄位（不洩漏密碼雜湊） |
| **Result type（Either）** | 顯式表示「成功或失敗」兩條路 | Rust 的 `Result<T, AppError>` + `?` 讓錯誤路徑幾乎零樣板 |
| **Active Model** | 實體物件自帶持久化行為 | SeaORM 的 `ActiveModel`：`courses::ActiveModel { course_id: Set(...), ... }.update(&tx)` |
| **Adapter（DB driver 抽換）** | 換掉底層實作不動上層 | SeaORM 同時支援 sqlx-sqlite 與 sqlx-postgres，靠 `DATABASE_URL` 切換 |

注意一個趨勢：傳統 GoF 的「裝飾者、工廠、觀察者」等模式，在現代語言與框架裡多半被吸收了——React 的 hooks、Rust 的 trait + 組合、SeaORM 的 `EntityTrait`，都是「同一件事的現代形式」。**學會認出模式背後的「形狀」比背模式名稱有價值。**

## 4.4　Agentic Coding：人機協同的程式碼生成

### 原理

Agentic Coding 是指：讓 AI 不只「生成一段程式碼」，而是參與**多步驟的開發循環**——理解規格、改程式、跑測試、看錯誤、再修正、更新文件。人類則負責：給方向、審查、決定、寫下一版規格。

有效的唱片（loop）長這樣：

```
1. 人：把需求/規格寫清楚（第二章的產物）
2. AI：照規格與專案既有模式，實作或修改
3. 人/AI：跑品質關卡（fmt → clippy → build → 測試）
4. AI：依測試失敗回饋自我修正
5. 人：Code Review，決定接受或打回
6. AI：更新文件/版本說明
7. 人：commit（中文訊息）
```

這個循環能不能跑得順，**取決於前三章的產物**：規格精確（2）、模組低耦合（3）、品質關卡可執行（4.1）。所以 Agentic Coding 不是「把鍵盤交給 AI」，而是「把工程紀律落實到 AI 也能遵守的程度」。

### 本專案例子：NQU-ERP 本身就是 Agentic 開發的產物

NQU-ERP 的 `AGENTS.md` 是一份「**給 AI 的工程規格**」，內容全是「AI 容易猜錯的事」：

> - 品質關卡：`cargo fmt && cargo clippy && cargo build && bash test.sh`，提交前必須全過。
> - 後端規則「退選後不可重選」：加退選 E2E 各用獨立課程，避免測試間污染狀態。
> - `getByText` name 匹配不分大小寫：`T001` 會命中 `t001@nqu.edu.tw`，要加 `exact: true`。
> - Vitest `include` 限定 `src/__tests__`，否則會抓到 `e2e/*.spec.ts`。

每一條都是「AI 第一次很可能犯、犯了會浪費時間」的坑。把這些寫成文件，Agent 的產出品質立刻上升。**寫 `AGENTS.md`、`_doc/vX.Y.md`、可執行測試，就是人在 Agentic 流程中的主要工作。**

實務上怎麼跟 AI 協作（從本專案的開發節奏總結）：

1. **一次只交代一個自包含任務**（加一支 API、修一個 edge case），不要一口氣要「全部做完」。
2. **給「要模仿的既有範例」**：說「照 `admin.rs` 的 `create_user` 模式加 `update_user`」比抽象描述快十倍。
3. **一定要跑品質關卡後才收**：AI 交回來的東西，先 `cargo test`/`npm test`，沒綠燈就不該 review。

## 4.5　Code Review 在 AI 時代的演變

### 傳統 Review 的重心

傳統 Code Review 檢查：語法風格、命名、明顯 bug、效能、安全、測試覆蓋。這些訊息量大、可程式化。

### AI 時代的 Review 重心

AI 生成（或 AI 大量協助的）程式碼，把傳統 Review 的項目自動化了（linter、formatter、`tsc`、`clippy`）。人類的 review 價值轉移到這幾件事：

1. **語意正確性**：AI 寫的程式「看起來對」，實際業務語意對嗎？例如衝堂條件寫反了沒。
2. **是否遵守規格與專案慣例**：這支 API 該有的權限檢查、Transaction、中文訊息、錯誤結構，是否與既有模式一致。
3. **範圍控制**：AI 常常「順手」改了原本沒要求的東西——reviewer 要抓「範圍外變更」。
4. **長期可維護性**：AI 偏好生成「當下最快通過測試」的 code，reviewer 要問「三個月後的人還讀得懂嗎」。
5. **測試品質**：AI 生成了測試，但測試是否真的在測對的行為？還是只是讓斷言通過的「假綠燈」？（第五章 5.4 深入）

### 本專案例子：一本「Review 檢查表」

把 `AGENTS.md` 與程式碼慣例翻譯成審查清單，審 NQU-ERP 的變更時逐條打勾：

- [ ] `cargo fmt && cargo clippy && cargo build` 全過，無 warning
- [ ] 角色權限：`auth.is_xxx()` 在第一行檢查，非該角色回 403
- [ ] 多表寫入用 `begin()` + `commit()`（TRANSACTION）
- [ ] 錯誤用 `AppError::bad_request/forbidden/not_found/internal`，中文訊息
- [ ] DTO 不多不少，不洩漏敏感欄位
- [ ] 沒加不必要的 comments；命名自我說明
- [ ] 對應的測試有更新（後端 `test.sh`、前端 Vitest/E2E）
- [ ] 沒有「範圍外的順手修改」
- [ ] 前端照既有元件模式（`CourseForm` 模式），沒有自創風格

> **AI 時代 Review 的終極形態**：人 review「AI 的產出」時，真正的檢查對象不是「程式碼對不對」，而是「**規格與程式碼的對帳（spec-code traceability）**」。把每一條需求對到一段程式碼與一個測試，AI 時代的 code review 才不會只剩「看起來可以」。

### 本章練習

1. **命名重構**：`grades` 的 `final_` 變數（`grade.rs:62`）是為了躲 Rust 保留字。討論是否有更自我說明的命名，並評估改名的風險。
2. **實際重構**：對 `course.rs` 的 `list_courses` / `get_teacher_courses` 做 4.2 的重構，重構前後各跑一次 `bash test.sh`，證明行為不變。
3. **模式辨識**：在 `src/middleware/auth.rs` 中找出「Extractor」模式的完整樣貌（type + rejection + error path），畫出它的生命週期。
4. **Review 實戰**：寫一段「有權限缺口 + 沒測試」的假新 API，用 4.5 的檢查表逐項打勾，寫出 review 意見。
5. **Agentic 指令練習**：用 4.4 的「給範例」技巧，寫一條給 AI 的指令：「照 `create_user` 的模式新增 `GET /admin/users/{id}` 單筆查詢」，並列出你預期 AI 會犯的三個錯。
