# 第一章　軟體工程的本質

> 本章用 NQU-ERP 校務系統作為貫穿案例。讀者應至少先看過 `_book/README.md` 的專案背景，並在原始碼中有 `src/main.rs`、`src/handlers/enrollment.rs`、`AGENTS.md` 幾個檔案可以對照。

## 1.1　什麼是軟體工程

軟體工程（Software Engineering）是「**運用工程化的原則、方法與工具，在時程與資源限制下，有紀律地開發與維護高品質軟體**」。它和「寫程式」的差別，就像「蓋房子」和「砌磚」的差別：砌磚是施工，蓋房子是規劃施工、控制成本、確保結構安全、處理水電管路，最後還要能長期維護。

一個清晰的分類方式是把它拆成幾個活動：

| 活動 | 要回答的問題 |
|------|--------------|
| 需求工程 | 到底要做什麼？給誰用？ |
| 系統設計 | 怎麼拆解成可管理的部分？ |
| 實作 | 怎麼把設計變成可執行的程式碼？ |
| 測試與品質保證 | 怎麼證明它做對了、不會被改壞？ |
| 部署與維運 | 怎麼上線、怎麼持續運作？ |

後續各章會逐一展開這五個活動。本節先用一個例子說明「寫程式 ≠ 軟體工程」。

### 本專案例子：把「選課」說清楚

如果只是「寫程式」，我們可能直接寫一段偽程式：

```
function enroll(student, course) {
  enrollments.insert(student, course)
}
```

如果是「軟體工程」，我們必須回答一連串問題，而 NQU-ERP 的 `src/handlers/enrollment.rs` 正是這些問題的答案：

| 問題 | 類型 | NQU-ERP 的答案（實作位置） |
|------|------|----------------------------|
| 學生是否可以選課？ | 權限 | `if !auth.is_student() { return Err(forbidden("只有學生可以選課")) }` |
| 已經選過怎麼辦？ | 業務規則 | 檢查既有 `enrollments`，回覆「您已選修過此課程」 |
| 退選過能否重選？ | 業務規則 | 回覆「已退選課程，請聯繫教務處重新選課」 |
| 和已選課程衝堂怎麼辦？ | 業務規則 | 三重迴圈比對時段，回報衝突節次 |
| 名額滿了怎麼辦？ | 資源限制 | `enrolled_count >= capacity` →「課程名額已滿」 |
| 多個動作一起失敗怎麼辦？ | 原子性 | `state.db.begin()` … `tx.commit()` 包住所有寫入 |
| 帳號不存在/沒權限？ | 錯誤路徑 | 一律回傳固定的 `{ "error": "..." }` 結構 |

「選課」在程式碼裡不是一行 `insert`，而是一系列**規則、檢查、交易與錯誤處理**的組合。把這些東西一一想清楚、寫下來、測試起來，就是軟體工程。

> **重點**：軟體工程的核心產物不只是程式碼，還有**規格、設計決策、測試與維運知識**。NQU-ERP 的 `_doc/` 底下每一版的 release notes、`AGENTS.md` 裡累積的「E2E 陷阱」，這些「非程式碼」的知識，正是軟體工程的具體成果。

## 1.2　軟體的複雜性與本質性困難

Fred Brooks 在 1987 年的經典論文《No Silver Bullet》指出，軟體的困難可分為兩類：

1. **本質性困難（Essential Complexity）**：來自問題本身，無法被工具消除。例如「如何讓學生衝堂檢查正確」、「如何保證名額不超收」。
2. **附屬性困難（Accidental Complexity）**：來自我們使用的語言、框架、工具「不理想」所造成的額外負擔。例如要寫一堆樣板程式碼（boilerplate）、設定編譯器、處理環境變數。

### 本專案例子：兩種困難的對比

NQU-ERP 的選課 API 裡，這兩種困難清楚可見。

**附屬性困難（碰巧存在，理論上可被工具減輕）：**

```rust
// 只為了把「一筆加選請求」從 JSON 轉成結構而寫的樣板
#[derive(Deserialize)]
pub struct EnrollRequest {
    pub course_id: i32,
}
```

像 `#[derive(Deserialize)]`、SeaORM 的 `ActiveModel`、Router 的路由設定……這些都是「工具不夠好，所以要我們多寫一點」的附屬性成本。改成 REST 框架也好、換語言也好，這些成本每重寫一次就付一次，但它們**可以**被更好的工具（或 AI）大幅消除。

**本質性困難（無論工具多好都存在）：**

```rust
for cs in &current_schedules {
    for ts in &target_schedules {
        if cs.day_of_week == ts.day_of_week
            && cs.start_period <= ts.end_period
            && ts.start_period <= cs.end_period
        {
            return Err(/* 報告與課程 X 衝堂，星期 N 第 a~b 節 */);
        }
    }
}
```

「兩個時段 [a, b] 與 [c, d] 同一天重疊 ⇔ `a <= d && c <= b`」這個條件判斷，是**本質性的**：它反映了校務世界的真實規則。不管用 C、Rust 還是 AI 生成，只要系統要做「衝堂檢查」，這條規則就必須被正確地表達出來。同樣地，「退選後不可重選」是立場決定，不是工具問題；「名額扣減必須原子化以免超賣」是資料一致性的本質要求。

> **重點**：辨認「這是本質性還是附屬性困難」是軟體工程師的基本判斷力。我們把精力放在本質性困難上，並用工具（或 AI）去消滅附屬性困難，而不是反過來。

## 1.3　人月神話與 Brooks 法則

《人月神話》（The Mythical Man-Month，1975）是 Brooks 的經典著作，幾個核心主張：

1. **人月不可換算（The Mythical Man-Month）**：一個工程師做 12 個月的工作，不等於 12 個工程師做 1 個月。因為溝通需要成本，工作也不一定可切割。
2. **Brooks 法則**：在一個已經落後的軟體專案上加人，只會讓它更落後。新增人手要時間上手，而且既有的溝通管道要重新調整（每人需要和其他每個人溝通，溝通連結數是 O(n²)）。
3. **第二系統效應**：工程師常常在第二個系統上，把第一個系統裡不敢加的奢華功能全部加上去，導致過度設計。
4. **Conway 定律**：系統的結構傾向於複製組織的溝通結構。兩隊人馬各自開發的模組，最後就像兩個部門的介面。

### 本專案例子：用版本演進對抗人月陷阱

NQU-ERP 的演進方式（見 `_doc/` 各版）刻意避開了人月神話的陷阱：

| Brooks 的警告 | NQU-ERP 的對策 |
|---------------|----------------|
| 一次做太大 → 人月不可換算 | 切成 v0.1→v0.4 可獨立驗收的小版本，每一版都有完整測試 |
| 第二系統效應（過度設計） | `_doc/plan.md` 明確標註「待 v0.4 / Future」，**先不做**的清單和要做的一樣重要 |
| 溝通成本隨人數上升 | 單人 + AI 協作團隊，溝通成本極低；靠 `AGENTS.md` 把「他人會踩的坑」寫成文件，用文件代替同步溝通 |
| Conway 定律 | 模組切分對齊角色權限（`handler` 一職責一檔），組織邊界刻意等於技術邊界 |

更進一步，這個專案把「加人會被拖慢」的問題，用**「加並行工具（AI）」**的方式部分避開——但這也帶出下一節的關鍵：AI 可以消除附屬性困難，卻無法消除本質性困難，因此「人月」換成「AI 月」也不能無限堆疊。

## 1.4　AI 時代：附屬性困難的消亡與本質性困難的永存

### 原理

生成式 AI（LLM）最適合的工作，正是那些「**高度重複、模式明確、低風險**」的附屬性困難：

- 框架樣板程式碼（`#[derive(...)]`、DTO struct、`getter/setter`）
- 語言的機械性轉換（ORM entity、migration 起手式）
- 文件的初稿、測試案例的骨架、正規表達式、設定檔

同時，AI **無法**（目前）替我們消滅本質性困難：

- 業務規則要**正確**（例如衝堂的區間判定）
- 系統整合要**一致**（前端顯示、後端驗證、資料庫約束三方一致）
- 效能與安全是**目標權衡**，不是填空題
- 需求本身是**模糊的**，需要人來決定

換句話說：**AI 讓「打字/查文件/寫樣板」變便宜，但讓「想清楚、做決策、驗證正確」變得更貴重**。這是 AI 時代軟體工程師最重要的認知。

### 本專案例子：什麼能被 AI 加速，什麼不能

以 NQU-ERP 的一個新增功能——「設定選課時程（v0.4 規劃中的 `enrollment-period`）」為例：

| 工作項目 | 困難類型 | AI 能幫到什麼程度 |
|----------|----------|-------------------|
| 寫 migration：新增 `enrollment_periods` 資料表 | 附屬性 | 高——照既有 6 個 migration 的樣式就能生 |
| 寫 handler 骨架：`POST /admin/enrollment-period` | 附屬性 | 高——照 `admin.rs` 既有模式（`auth.is_admin()` + DTO + response） |
| 前端再加一個下拉表單 + API 呼叫 | 附屬性 | 高——照 `CourseForm.tsx` 模式 |
| **決定**「預選、正選、加退選期間互相不能重疊，且只能在指定期間加選」的規則怎麼查、回什麼錯 | 本質性 | **低**——這是立場與領域規則，AI 只能提議，人決定 |
| **驗證**「在擴大加選期間狀態下，原本 72 個測試仍全過、兩地時區的教務處運作正常」 | 本質性（驗證） | 中——AI 可以跑測試與提議用例，但「接受上線」是人負責 |

本書之後各章會反覆回到這條界線：**AI 負責產出，人負責判斷與驗證**。這在第二章（規格）、第四章（Agentic Coding）、第五章（LLM-as-a-Judge）會有更深的展開。

## 1.5　軟體工程師的角色轉變

### 原理

在大模型之前，軟體工程師的大量時間花在「寫程式」與「找語法/框架的坑」。AI 時代，這些工作的單位成本劇降，工程師的角色向三個方向轉變：

1. **規格與評審者（Specifier & Reviewer）**：把模糊需求寫成 AI 能理解的精確規格，並審查 AI 的產出是否正確。
2. **軟權重與決策者（Architect & Decision-maker）**：決定邊界（做與不做）、取捨（效能 vs 簡單）、介面（API 長相）。
3. **整合者與值班者（Integrator & Operator）**：把 AI 產出和團隊/系統整合，並負起上線後的成敗。

角色的「程式碼生產」成分下降，「**批判性閱讀、測試設計、部署維運**」的成分上升。

### 本專案例子：從「我們怎麼開發的」看新角色

NQU-ERP 的 `AGENTS.md` 本身就是角色轉變的證據。一個普通的專案不需要「給 AI 看得開發指南」，但這個專案有，且內容非常具體：

> 「`getByText` / `getByRole('cell')` name 匹配不區分大小寫：`T001` 會命中 `t001@nqu.edu.tw` → 加 `exact: true`」

這是**人類把踩過的坑，寫成機器可遵循的規格**。在 AI 協作開發中：

- 人負責把「經驗」變成「文件/規格」（`AGENTS.md`、`_doc/*.md`、`test.sh` 的斷言）
- AI 負責把「規格」變成「程式碼」並自我驗證
- 人負責在關鍵節點做最終判斷（是否接受 AI 的解決方案）

另一個角色轉變的例子是**品質關卡由人手工執行變為腳本化**（第一章就強調）：`cargo fmt && cargo clippy && cargo build && bash test.sh`。當「品質檢查」從「靠記憶的專業技能」變成「可執行的命令」，工程師就能把注意力放在更高層的決策上。
