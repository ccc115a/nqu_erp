# 第六章　部署與維運

> 軟體「寫得出來」和「活得下去」是兩回事。本章談如何把 NQU-ERP 從開發機搬到正式環境，並讓它在被攻擊、被塞爆、當機時還能被發現、恢復與自癒。

---

## 6.1　CI/CD 管線設計

### 原理

CI（Continuous Integration）＝**每次合併前自動驗證**：build、lint、單元/整合測試，讓「壞程式碼」在最接近產生的時點被攔下。CD（Continuous Delivery/Deployment）＝**通過驗證就自動上線**。

管線的價值在於**關卡（gate）**，每一關都有明確的失敗條件：

```
程式碼 push
  │
  ▼ 建置（build）
  ├─ 失敗 → 紅，工程師看到就修
  ▼ Lint / 格式（fmt、clippy）
  ├─ 失敗 → 紅
  ▼ 測試（單元 → 整合 → E2E）
  ├─ 失敗 → 紅
  ▼ 部署（staging → production）
```

### 本專案例子：把「在地品質關卡」搬成 CI

NQU-ERP 的品質關卡目前是「人記得跑」的 bash 腳本。把它升級成 CI 只需要把同樣的步驟搬進 GitHub Actions：

```yaml
name: CI　# GitHub Actions 範例

on: [push, pull_request]

jobs:
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - run: cargo fmt --check && cargo clippy -- -D warnings
      - run: cargo build
      - run: bash test.sh        # 整合測試（build→server→seed→API）

  frontend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm, cache-dependency-path: frontend/package-lock.json }
      - run: npm ci
        working-directory: frontend
      - run: bash test.sh        # 含 Vitest + Playwright
        working-directory: frontend
      - uses: actions/upload-artifact@v4  # 保留 Playwright 失敗的畫面
        with: { name: playwright-report, path: frontend/playwright-report/ }
        if: failure()
```

發現幾件在 CI 化時才浮現的事（這就是 CI 的價值——逼你把環境說清楚）：

1. **測試依賴本機順序**：`test.sh` 假定「沒有別人在跑 :8080」── CI 要用乾淨 runner，這假設才能成立。
2. **DB 重置**：`test.sh` 直接 `rm -f dev.db`，CI 每個 job 都是全新環境，正好符合「immutable」精神。
3. **E2E 需要瀏覽器**：Playwright 要裝 `npx playwright install`，CI 腳本裡要明確寫出來。
4. **seed 的 Python 依賴**（`faker`、`bcrypt`）：要寫成 `requirements.txt` 或在 `set -euo pipefail` 下先驗證，否則 seed 失敗會很隱晦。

**12-Factor 的痕跡**（`config.rs`）：所有設定走環境變數（`DATABASE_URL` / `JWT_SECRET` / `SERVER_ADDR`），CI/CD 才能對「同一個 binary、不同環境」以不同設定部署。這是可部署性的基石。

## 6.2　DevOps 與基礎設施即程式碼

### 原理

DevOps 的核心：**開發與維運同一個團隊的責任**，用「可重現、可自動化」取代「神秘操作手冊」。基礎設施即程式碼（IaC）把伺服器、資料庫、部署流程寫成程式/設定檔，做到：版本控制、可重現、可審查、可回滾。

NQU-ERP 現有的「自動化殘跡」就是小型 IaC：`run.sh` 把「建置 → 重置 DB → seed → 起前後端」整個流程寫成一支腳本；`run_seed.sh` 把 seed 變成一鍵指令。把它們升級成真正的部署自動化，下一步是容器化。

### 本專案例子：用 Docker 把環境「打包」

`Dockerfile`（後端示意）：

```dockerfile
FROM rust:1.80 AS builder
WORKDIR /app
COPY . .
RUN cargo build --release

FROM debian:bookworm-slim
COPY --from=builder /app/target/release/nqu-erp /usr/local/bin/nqu-erp
COPY migrations /app/migrations
EXPOSE 8080
ENTRYPOINT ["nqu-erp"]
```

`docker-compose.yml`（+ 生產 DB）：

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: nqu
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes: [pgdata:/var/lib/postgresql/data]
  api:
    build: .
    environment:
      DATABASE_URL: postgres://nqu:${POSTGRES_PASSWORD}@db:5432/nqu_db
      JWT_SECRET: ${JWT_SECRET}
      SERVER_ADDR: 0.0.0.0:8080
    depends_on: [db]
    ports: ["8080:8080"]
volumes:
  pgdata:
```

Docker 化的收益正好對上 3.1 的抽象講：**「環境」也變成一個可替換的抽象**了。新版 Docker 對正式環境的紀律：`JWT_SECRET` 與 `POSTGRES_PASSWORD` 必須從祕密管理（secret manager）注入，**絕不能 commit 進 repo**（`AGENTS.md` 已把 `.env` 放進 `.gitignore`）。

## 6.3　監控、日誌與可觀測性

### 三支柱

| 支柱 | 問題 | NQU-ERP 現況 |
|------|------|--------------|
| **Logs（日誌）** | 出了什麼事？ | ✅ 已有 `tracing_subscriber` + `AppError` 會記 DB 錯誤（`errors.rs:55`） |
| **Metrics（度量）** | 現在發生了多少事？（QPS、延遲、錯誤率） | ❌ 尚未引入 |
| **Traces（追蹤）** | 一個請求從頭到尾走了哪些路？ | ⚠️ 單體內部可推測，跨服務需要 trace |

### 本專案例子：把現況升級成「可觀測」

NQU-ERP 已有的可觀測性地基：

1. **/health 端點**：`GET /health` 回 `"OK"`，`test.sh` 用它做就緒探測（readiness probe），第六層監控也用它做心跳——一個乾淨的接口就是維運的起點。
2. **啟動即 migration**：`main.rs` 在 listen 之前跑完 migration才啟動，失敗就退（fail-fast），避免「半裸 server」接受流量。

缺少的部分與升級方向（用 Rust tracing 生態即可做到）：

```rust
// 現況（一行式）：
tracing_subscriber::registry().with(tracing_subscriber::fmt::layer()).init();

// 升級方向：structured logging + 每請求 span
//  - 每一支 handler 進來就開 span!("enroll_course", user=%auth.user_id)
//  - 錯誤發生時 tracing::warn!("conflict", course=%payload.course_id)
//  - 輸出 JSON logs（tracing-stackdriver / tracing-subscriber JSON feature）
//  → 就能在監控平台回答「這類 400 每天多少次、集中在哪門課」
```

再補上 metrics（例如 `metrics` crate 量去 per-endpoint latency / 5xx 計數）與 alert rule（錯誤率 > 5% → 值班告警），一套完整的可觀測性就成形了。

**可觀測性的 AI 時代意義**：被餵給「自癒系統」的資料越結構化，第 6.4 的 AI 異常偵測就越可靠——**垃圾日誌進，垃圾判讀出**。

## 6.4　AI 驅動的異常偵測與自癒系統

### 原理

傳統維運是「人看 dashboard → 人下指令」。AI 驅動的維運把這個週期自動化：

```
收集（logs/metrics/traces）
  → 偵測（AI 找出「不像平常」的模式）
  → 診斷（AI/規則 論斷原因）
  → 自癒（自動復原 + 回報）
  → 學習（把復原步驟寫進知識庫）
```

**自癒的金字塔要一層一層來**，不要一步到位：

| 層級 | 做法 | NQU-ERP 對應 |
|------|------|--------------|
| L1 自動重啟 | 健康檢查失敗 → 自動重啟容器 | `/health` 已是現成探測 |
| L2 自動擴縮容 | QPS 超過閾值 → 加開實例 | 目前單體，先手動水平擴展（6.2） |
| L3 自動降載 | 高峰時拒絕非必要流量（如報表） | 選課高峰可設定護航規則 |
| L4 AI 判讀 | LLM 讀 log、摘要根因、提修復建議 | 需先把日誌結構化（6.3） |

### 本專案例子：設計 NQU-ERP 的「LA（自癒）」方案

以「選課高峰瞬間湧入」這個最務實的情境，設計階梯式自癒：

```
情境：加選開始的 10 分鐘，POST /enrollments 流量暴增 20 倍

L1（自動重啟）
  - /health 探測失敗 → 重啟容器（秒級）

L2（保護性行為）
  - 在應用層對 /enrollments 限流（rate limit）：超過閾值回 429
  - 前端 axios 攔截 429 → 顯示「人數眾多請稍後再試」（而不是讓使用者看到噴錯）

L3（AI 判讀）
  - 將 /health 的狀態、錯誤率指標、日誌喂給 LLM：
      prompt: 「這是選課高峰期間的錯誤日誌與指標。請診斷是否有異常，
              若是預期的限流行為請說明，並給出繼續調參的建議。」
  - LLM 回報 → 人確認 → 調限流閾值（人保留最終決定）

L4（自癒 + 學習）
  - 每次「重啟 / 限流 / 調參」都寫回維運行事曆
  - Agent 把「衝堂檢查在高峰瞬時 2000 req/s 的表現」也納入壓力測試
    （這正是 plan.md 的 v0.5 規劃：Redis 名額快取、500+ RPS 壓力測試）
```

設計要領：

1. **先有完整的手動操作手冊，才能自動化**——「人確定會做的事」AI 才值得代勞。
2. **自癒動作必須可逆、可審計**——記錄每一次「AI 做了什麼」，讓它能被檢討（對齊 5.5 的「人保留最終決定權」）。
3. **不要的雜訊不餵 AI**——log 要先結構化、去敏感化（不能把學生個資送進第三方 LLM）。

監控、偵測、自癒都建立在「能對 stack 下指令」之上。這節把 NQU-ERP **實際的維運指令**收錄成書——不是教科書理想，而是本 repo 現役、可親手執行的命令。

### 一鍵維運腳本：`docker_run.sh`

專案根放了一支把「起停 / 看 log / 查狀態」合一的腳本（`set -u` 保護，避免未初始化變數在 CI 噴 `unbound variable`）：

```bash
bash docker_run.sh              # 啟動／上線（預設 WEB_PORT=80）
bash docker_run.sh 3000         # 指定對外 port 上線（http://localhost:3000）
bash docker_run.sh stop         # 停止，保留資料（volume 不動）
bash docker_run.sh restart      # 重啟
bash docker_run.sh logs [svc]   # 跟 log（可指定 db/api/web）
bash docker_run.sh status       # 看目前狀態
bash docker_run.sh down         # 停止並清空資料（-v；慎用）
```

它的核心是**單一 dispatcher + 上線路徑分離**，避免「參數當 port」與「子命令」互相干擾的兩段式陷阱：

```bash
case "${1:-}" in
stop|restart|logs|status|down)   # 維運子命令：用完即 exit
  MODE="$1"; shift 2>/dev/null || true
  ;;
*)
  MODE=""
  ;;
esac
[ -n "$MODE" ] || WEB_PORT="${1:-}"   # 其餘 = 上線；第一個參數是 port
```

排版的實戰教訓（本書作者踩過）：**不要寫「兩層獨立 case 都讀 `$1`」的 dispatcher**——`shift` 之後 `$1` 已空，第二層 case 會落空而誤走上線路徑、把「stop」當成啟動。正確做法是**先 `case` 設定 MODE、`shift`，之後一律以 `$MODE` 條件分支**（上面的寫法），或乾脆把子命令各自 `exit`（`docker_run.sh` 目前採用後者）。

執行實例（本專案實測輸出，資料均保留）：

```
$ bash docker_run.sh stop
── 停止 stack（保留資料）...
 Container nqu_erp-api-1  Stopped
 Container nqu_erp-db-1   Stopped
 Container nqu_erp-web-1  Stopped

$ docker compose ps          # 驗證：已全停、資料仍在 volume
NAME            STATUS

$ bash docker_run.sh 3000    # 換 port 重上線
✅ NQU-ERP 已上線： http://localhost:3000
（資料庫已有資料 → 跳過 seed，volume 資料直接接續）
```

### Web 服務對外 port：`WEB_PORT`

`docker-compose.yml` 的 web 用「環境變數帶預設值」做到同一個映像、可換 port：

```yaml
services:
  web:
    build: ./frontend
    ports:
      - "${WEB_PORT:-80}:80"    # 預設 80；指定 3000 → 3000:80
```

```bash
WEB_PORT=3000 bash docker_run.sh   # 或等價：bash docker_run.sh 3000
```

> 注意：`api` 是**不往 host 暴露**的（僅 nginx 同源 `/api` 代理）。這是刻意的——本機 `test.sh` 佔用 `:8080`，若 api 同時綁 8080 會打到容器造成測試誤判（v0.4 實測踩過）。**暴露出去的永遠只有一個入口：web 的 nginx**。

### 從 GHCR 一鍵拉取上線（CD 產物）

v0.5 的 CD 把映像推上 `ghcr.io`，正式主機不必有 Rust toolchain，只需 Docker：

```bash
# 目標主機（首次先登入 GHCR，用 GITHUB_TOKEN / PAT）
echo "$GHCR_TOKEN" | docker login ghcr.io -u <你的帳號> --password-stdin

# 拉取並上線（同一個 compose 設定，web 對外 port 照樣可指定）
WEB_PORT=80 docker compose pull   # 拉 api / web 映像
bash docker_run.sh                 # 一鍵上線（連 db 一起）
```

> 部署仍保留「人」最後一關：CI 全綠 + CD 推完映像 ≠ 自動 deploy。NQU-ERP 把 deploy 留在**目標主機手動 `bash docker_run.sh`**，正是 6.1「關卡」哲學的延伸——機器幫你驗證 + 備好映像，人按鈕上線。

## 6.5　維運指令實作（本專案 Docker）

前面 6.1–6.4 是「原則」；這節把 NQU-ERP **實際可跑**的維運指令整個攤開——不是教科書範本，而是 repo 裡現役 `docker_run.sh` / `docker_test.sh` / `github.sh` 三支腳本的職責分工與真實語法。

### 三支腳本：職責分工

| 腳本 | 職責 | 何時用 |
|------|------|--------|
| `docker_run.sh` | **上線 + 維運**：start / stop / restart / logs / status / down | 正式環境，天天用 |
| `docker_test.sh` | **整合驗證**：build → up → seed → 23 項測試 → 收尾 | CI 的 Docker job、改動後自測 |
| `github.sh` | **add / commit / push** 一鍵完成（含敏感檔攔截） | 每次要上 GitHub 時 |

> 三支拆開的原因＝**單一職責**：驗證（test）與營運（run）若混在一起，維運時會不小心重置資料；`github.sh` 獨立則讓「上線」與「送 repo」分明（呼應 5.4 的資安關卡）。

### `docker_run.sh` — 一鍵維運

```bash
bash docker_run.sh              # 上線（預設 port 80）
bash docker_run.sh 3000         # 指定對外 WEB_PORT=3000 上線
bash docker_run.sh stop         # 停止（保留資料）
bash docker_run.sh restart      # 重啟
bash docker_run.sh logs         # 追 log（可加服務名 db/api/web）
bash docker_run.sh status       # 看 stack 狀態
bash docker_run.sh down         # 停止並清空資料（下 -v）
```

實際語法（節錄，完整見 repo）：

```bash
set -u
case "${1:-}" in
stop)  $COMPOSE stop;      exit 0;;
restart) $COMPOSE restart; exit 0;;
down) $COMPOSE down -v;    exit 0;;
logs) $COMPOSE logs -f "${2:-}"; exit 0;;
status) $COMPOSE ps;       exit 0;;
esac
[ -n "$WEB_PORT" ] || WEB_PORT="${1:-}"   # 其餘參數視為 port
# 然後 $COMPOSE up -d --wait + 依 DB 是否為空決定 seed
```

> **確定的陷阱**：若用 `set -u`（推薦）但沒先給 `WEB_PORT` 預設值，`stop`/`restart` 等子命令就會炸 `WEB_PORT: unbound variable`（本專案在 v0.5 實測撞到過）。**上線路徑才讀 port；子命令路徑要 `exit` 於讀 port 之前**。

### `WEB_PORT`：對外 port 由環境變數決定

`docker-compose.yml` 的 web 服務這樣接同一個映像、可換對外 port：

```yaml
services:
  web:
    build: ./frontend
    ports: ["${WEB_PORT:-80}:80"]   # 預設 80；bash docker_run.sh 3000 → 3000:80
```

維運時若要避開 80（例如本機 80 被 nginx 佔用），**位置參數優先**（與 repo 的 `WEB_PORT="${1:-}"` 一致；env 寫法會被位置參數覆蓋，別並用）：

```bash
bash docker_run.sh 8080        # 對外 8080 → 容器內 80
curl http://localhost:8080/api/v1/health

### 從 GHCR 一鍵拉取上線（v0.5 CD 產物）

CI 全綠後，CD 自動把 API / Web 映像推到 GHCR（`ghcr.io/ccc115a/nqu_erp-{api,web}:main`）。正式主機**不必有 Rust toolchain**，只有 Docker 即可上線：

```bash
# 正式主機：只拉 + 上線
echo "$GHCR_TOKEN" | docker login ghcr.io -u ccc115a --password-stdin
WEB_PORT=80 docker compose pull          # 拉 api / web 映像
bash docker_run.sh                       # 上線（seed 邏輯同前，資料第一次會自動 feed）
curl http://localhost/api/v1/health      # 驗證
```

> 這呼應 6.1 的關卡哲學：**CD 只負責「備好映像」，放最後的「上線」仍由人按鈕**（`bash docker_run.sh`）——保留人為最終決定權（對齊 5.5）。

### 本章練習

1. **把品質關卡送上 CI**：用 6.1 的 GitHub Actions 範本，實作出 `backend` / `frontend` 兩個 job，跑在你自己的 repo 上驗證會過。
2. **Docker 化**：為後端寫 Dockerfile + docker-compose（含 PostgreSQL），並驗證 `docker compose up` 後 `/health` 為 `OK`。觀察要改幾行程式碼（應為 0）。

5. **自癒方案審查**：為「成績送交後使用者抱怨看不到」假設一個事故，用 6.4 的 L1–L4 分層設計對應的偵測與自癒，並用 4.5 的審查心態檢討你的方案可能漏了什麼。
